# 出新 build 的規則

> 2026-08-23 立。起因：1.4.9 (75) 上架後才發現它比 1.4.8 (68) **少了一整批功能**——
> 一顆合併（`63e38b2`）把 `index.html` 整檔取了 main 那一側，凡「只活在 App 線、沒併進 main」
> 的內容當場全部消失。build 成功、archive 成功、既有 verify 全綠，**沒有任何一道閘門會紅**。
> 這份規則就是為了讓同一種事故下次一定會被擋在上傳之前。

## 一、每顆 build 出貨前必過的四道

1. **`npm run verify`（含出貨回歸閘門）**
   `app/scripts/verify_no_ship_regression.mjs` 已接進 `verify-release.mjs`，出貨鏈上自動跑到。
   它比對七類識別字（函式／元素 id／更新紀錄 `data-cl`／說明中心節 key／方案面板功能項／
   旗標常數／URL 參數），基線是 `app/shipped-baseline.json`。
   **紅了不准改基線放行**，三條出路寫在腳本的錯誤訊息裡。

1b. **基線必須涵蓋線上現行版**（2026-08-30 加）
   `shipped-baseline.json` 是人手動 `--update` 推進的，沒人推它就停在更早那一顆，於是
   「沒有任何一項比已上架的少」比的是舊的那一顆——**閘門全綠、訊息還很大聲，只是它口中的
   「已上架」是錯的**。`set-release-mode.mjs` 現在會在動 pbxproj 之前實查線上版號，
   基線落後就 exit 4 並印出推進指令（離線查不到則只警告放行）。

1c. **另一條線有而這條線沒有的，要逐顆裁定**（2026-08-30 使用者裁示）
   兩條出貨線（iOS `build/app-*`、Android `build/android-*`）會各自長東西，而**回歸閘門的
   基線只認自己這條線出過的顆**，跨線遺漏它一個字都照不到（`f9d16df` 英日名牌讓位在
   Android 21 上，iOS 83 第一次打包時整個沒有，是使用者實機看到才發現的）。

   ⚠️ **2026-09-01 訂正做法**：原本寫的是逐顆 `git log --oneline <本線>..<對方線>` 裁定。
   那個做法**已經失效**——08-31 改寫過歷史（把送審文字移出 public repo），舊出貨分支的 SHA
   全部對不上，`origin/main..build/app-1.5.2-83` 會列出 **59 顆「缺漏」而內容其實都在 main**。
   一份全是假陽性的清單，人只會學會忽略它。

   改用**內容層**判準——比對識別字，不比對 commit：

   ```bash
   node app/scripts/verify_no_ship_regression.mjs --cand index.html
   ```

   基線用「**所有還在使用者手上的載貨**」（見第二節），跨線遺漏就會以「少了哪個識別字」
   的形式現形。`git log` 只在你想知道**為什麼**少了那一項時才拿來查，不當閘門。

2. **確認這顆的 version train 還開著**
   ASC 只讓「短版本字串等於版本紀錄版號」的 build 被選進去，**已上架的 train 會被回絕**。
   線上現行版號用帶 no-cache 的 lookup 實查（裸 URL 會拿到 CDN 舊值）：

   ```bash
   curl -s -H 'Cache-Control: no-cache' "https://itunes.apple.com/lookup?id=6792673516&t=$(date +%s)" | python3 -c "import sys,json;d=json.load(sys.stdin)['results'][0];print(d['version'], d['currentVersionReleaseDate'])"
   ```

   線上版號 == 你要掛的行銷版號 ⇒ **那個 train 已關**，必須進位（例：1.4.9 已上架 ⇒ 改開 1.4.10）。
   這件事要在**打包之前**查，不是打完才查。

3. **「更新了什麼」有寫**
   `set-release-mode.mjs` 的 `why` 同時是 App Store What's New 與 App 內彈窗。
   ⚠️ 既有閘門只檢查 why 裡有沒有**行銷版號**，所以「marketing 不動、只升 build 號」時它擋不住
   忘改 why——那種形狀要自己看一眼。

4. **build 號只進不重用**
   一個 build 號只能對應一份載貨。作廢的 archive 就讓它作廢，**不要用同一個號重打**——
   「同號兩份不同內容」正是這整串事故最難查的地方。

## 二、基線什麼時候可以推進

**只有在那一顆真的上傳成功之後**：

```bash
node app/scripts/verify_no_ship_regression.mjs --update \
  --from <上一顆已上架的 index.html>,<這一顆的 index.html> \
  --marketing <版號> --build <build 號>
```

`--from` 要給**所有還在使用者手上的 build**（不是只有最新那顆）。
08-23 丟掉的正是「68 有、75 沒有」——只拿 75 當基線的話，那次損失連被發現的機會都沒有。

## 三、合併進 App 線之前

`index.html` 在 App 線與 main 線都會被改，而且**兩邊的內容不是彼此的超集**。
合併時：

- **絕不整檔取單邊**（`git checkout --theirs/--ours <檔>`、或把衝突檔直接複製過去）。
  判斷方法：合併完 `git diff <合併結果> <被併掉那一側>` 若為空，就是整檔取單邊了。
- 三方比對用 `git merge-file --diff3`，衝突逐一手裁。
- 合併後跑一次出貨回歸閘門（`node app/scripts/verify_no_ship_regression.mjs --cand index.html`），
  它會直接列出被吃掉的識別字。

## 四、既有 verify 的一個結構性弱點

`verify_plus_ctas.mjs` 與 `verify_boot_geo.mjs` 從 08-22 起就一路紅——**但它們不在出貨鏈上**，
沒有人會在出 build 的時候跑到，所以紅了三天沒人看見。
⇒ 新寫的驗收腳本若涵蓋「使用者看得到的功能」，就要嘛接進 `verify-release.mjs`，
要嘛接進每日巡檢；放在 repo 裡等人想到才跑 == 沒有這支腳本。

## 五、iOS 出檔：唯一流程

> 2026-09-01 立。起因：連續幾次出 iOS build，每一次的做法與說法都不一樣——有時說 archive
> 得自己在 Xcode 裡按，有時直接用 CLI 出；步驟順序也每次重編一遍。這一節是這件事的
> **唯一正本**——`set-release-mode.mjs`、`patch-archive-os.mjs` 全部只准指向這裡，
> 不准各自再寫一份。

### 為什麼會每次都不一樣（根因，不是藉口）

流程原本寫在**程式碼註解**裡，而註解是跟著分支走的。2026-09-01 當天的實況：

| 讀到哪一份 | 它說 |
|---|---|
| `origin/main` 的 `set-release-mode.mjs` 檔頭 | archive 我做得到（當天訂正過） |
| `build/app-1.5.3-86` 的**同一支腳本**檔頭 | archive 做不到，你要自己按 Product ▸ Archive |

出 build 是在 build 線做的 ⇒ 讀到的是舊的那份 ⇒ 我照著它跟使用者說「archive 我做不到」。
使用者於是自己 archive 了一顆等我 patch；我的 CLI archive 在 57 秒後落地。
**同一個 build 號底下出現兩顆 archive，我 patch 我那顆、使用者上傳他那顆**，
ASC 回 ITMS-90111，86 這個號燒掉。

⇒ 修法不是再寫一份更好的註解，是**把流程變成一支可執行的指令**。能被執行的東西沒有詮釋空間。

### 能力邊界（實測，不是推測）

| 步驟 | 誰做 | 證據 |
|---|---|---|
| 設版號／旗標／建 www／cap sync／發行閘門 | **我** | 每顆 build 都在跑 |
| `xcodebuild … archive` | **我** | 2026-09-01 實測 `ARCHIVE SUCCEEDED`，同日出過 86／87 兩顆。開發憑證就簽得出 archive |
| `patch-archive-os`（拿掉 beta macOS 標記） | **我** | 同上 |
| 上傳前閘門 | **我** | `verify_archive_ready.mjs` |
| **Organizer ▸ Distribute App ▸ Upload** | **只有使用者** | 本機鑰匙圈沒有 Distribution 憑證；那一步當場申請並**重簽**，而 patch 破壞的簽章正是靠它補回來 |

🔴 **這張表上「我做得到」的那四格，不准因為讀到別處的舊註解就改口。**
能力邊界的**否定式**斷言（「我做不到 X」）成本不對稱：誤以為做得到，最多浪費一輪就當場拿到真相；
誤以為做不到，會**無聲地**把工作丟回給使用者，而且沒有任何訊號告訴你判斷錯了。
要推翻這張表，只能靠**當場實測**，不能靠任何一段註解或記憶。

### 流程（就這一行）

```bash
node app/scripts/ios-release.mjs feature      # 正式送審
node app/scripts/ios-release.mjs testflight   # TestFlight
```

它依序做六步，任一步紅就停：

1. **這是哪棵樹** — 印出樹路徑、分支、HEAD、落後 `origin/main` 幾顆、未提交檔數。
   讀錯樹＝出錯貨，所以先自證來源。
2. **`set-release-mode <模式>`** — version train 實查、出貨基線涵蓋檢查、寫 pbxproj 並回讀、
   `prepare-web`、`cap sync`、`npm run verify`。
3. **build 號未被用過** — 掃 `~/Library/Developer/Xcode/Archives`，同版號已有 archive 就**拒絕**（規則四）。
4. **`xcodebuild … archive`** — scheme 固定 `App`、derivedData 固定 `app/ios/DerivedData`、
   檔名固定 `軌島-<版>-<build>-<網頁BUILD>.xcarchive`。
5. **`patch-archive-os <剛才那顆的路徑>`** — 明講路徑，不讓它自己挑「mtime 最新」。
6. **`verify_archive_ready`** — 上傳前閘門，綠了才印出要在 Organizer 挑哪一顆。

出完之後、交給使用者之前（或使用者隔天才要上傳時），**可以單獨重跑閘門**：

```bash
node app/scripts/verify_archive_ready.mjs
```

### 閘門在擋什麼

| | 擋的事 | 為什麼 |
|---|---|---|
| C1 | 同版號在 Archives 底下只准有**一顆** | Organizer 只顯示「App／日期／版本」，兩顆長得一模一樣。**有兩顆時「哪顆對」這個問題本身就沒有安全答案** |
| C2 | archive 的載貨與這棵樹逐 byte 相同 | 中間跑過 `build:release`（出 Android）會把 `app/www` 換成 Android 版 |
| C3 | 小工具 extension 有被打進去 | 09-01 使用者那顆是用 `RailBoardWidgetExtension` scheme 出的，照樣有 App.app、版號也對 |
| C4 | `.app` 內版號 == 要出的版號 | |
| C5 | 全 archive 零個 beta `BuildMachineOSBuild` | 沒 patch 就上傳 ⇒ ITMS-90111 ⇒ 號燒掉 |
| C6 | 工具鏈非 beta、`MinimumOSVersion` 15.0 | 這兩件改 plist 救不了，只能重 archive |

C1／C5 兩條在 2026-09-01 用當天那兩顆作廢 archive 當控制組驗過會紅（`RAIL_ARCHIVES_ROOT` 指過去）。

### 非談判條款

1. **一個 build 號只對應一份載貨**（規則四）。作廢的 archive 搬去
   `~/Library/Developer/Xcode/_已作廢的archive/<版>-<build>/`，**檔名寫清楚為什麼作廢**，
   下一顆換新號。歷史上光是 1.5.2 (83) 就在磁碟上留了四顆同號 archive。
2. **不要請使用者自己 archive**。他一 archive 就會出現同號兩顆——這就是 86 的死法。
3. **先 iOS，再 Android**。Android 的 `build:release` 會覆蓋 `app/www`；順序反了，
   `patch-archive-os` 與 C2 都會誤報「這顆 archive 不是這棵樹建出來的」
   （修法：重跑一次 `set-release-mode <模式>` 讓 www 回到 iOS 版，**不必重 archive**）。
4. **交給使用者時只給一句話**：Organizer 裡挑哪一顆（閘門會把名字印出來）＋ Distribute App ▸
   App Store Connect ▸ Upload。不要再附上「或者你也可以…」。
5. **要改流程就改 `ios-release.mjs` 與這一節**，不要在別的檔頭註解裡另立說法。
