## 發現

### F1（P0）續推會產生「已離站但 run=0」的車，前端整包名冊判 malformed
- `coastForward`（`scripts/trtc_official_roster.mjs:434-449`）只回 `{from,to,arrEpoch,coasted}`，
  `carried()`（同檔 `484-489`）原樣併回車上 ⇒ **`run` 與 `terminal` 不會跟著改**。
  起點車（`terminal:true, from===to, run===0`）被 carry 後續推一站，就變成 `from!==to` 而 `run` 仍是 `0`。
- 前端 guard `index.html:17443-17445`：`(from === to ? run === 0 : to === from + step && run > 0)`；
  迴圈內任一台不合法就 `return false`（`17431-17455`）⇒ `applyTrtcOfficialRoster` 走
  `trtcOfficialRosterHold('malformed')`（`17476`）＝**整包不套用**。
- 實測（正式站，2026-08-17 10:35:11–10:37:11，連續 9 輪）：每一輪都有 2 台違規
  （`ov:2026-08-17:0000s2` G_XBT `1>0 run=0 carried,coasted`、`ov:2026-08-17:0000sq` R_XBT `0>1 run=0`）。
  語料重放：264 台次、**56/56 輪全中**。
- 畫面症狀：`?officialroster=1`（或把預設開回來）時，名冊停在最後一份被接受的版本
  （`trtcOfficialRosterActive:4820-4825` 沒有資料齡閘 ⇒ 舊名冊會一直畫），車跑到自己的 arrEpoch
  之後由前端續推、與真實脫節；若從未接受過任何一份 ⇒ `trtcOfficialRosterOutage` ⇒ 北捷列車全部消失、
  跟車被清掉並跳「列車已離開官方即時名冊」。實測旁證：三次瀏覽器實驗中，兩次在 60–90 秒內名冊完全沒套上
  （payload 帶著那兩台 XBT 幽靈），唯一成功的一次發生在 payload 乾淨的 `at=1786934066` 那輪。

### F2（P0）續推把「停滯退場地板」架空：幽靈最長活 29 分鐘、疊車變三倍
- 地板錨在車自己的 `arrEpoch`（`projectedRetireOf:332-346`＝`arrEpoch + cycle×3`），
  而 `carried()` 每輪把 `arrEpoch` 往前推 ⇒ 門檻跟著往後跑；另外 `carriedVehicle:479`
  對「已算得出 retireEpoch」的車**直接短路**，地板結構上不適用（實測 406 台次）。
- 突變對照（同一份語料、只換續推開關）：

  | | 現行（有續推） | 關掉續推 | 續推＋補 routePosition |
  |---|---|---|---|
  | 車數/輪 | 191.9 | 176.9 | 194.8 |
  | 官方列/輪 | 164.9 | 164.9 | 164.9 |
  | carried（無官方列撐腰）/輪 | 48.5 | 33.0 | 48.4 |
  | 同段≥3 台 | **224 段次**（最擠 5） | 84（最擠 4） | 219（最擠 6） |
  | exits 合計 | 74 | 114 | 80 |
  | 自己的到站時刻已過 120s+ | 2.2/輪 | 10.6/輪 | 1.9/輪 |

  ⇒ 續推把「停著的殘骸」換成「會跑的幽靈」，總量與疊車都更糟。
- 幽靈壽命（距最後一次官方確認）：n=2715，中位 **150s**、p90 **765s**、最長 **1741s**。
  最久那台 `ov:2026-08-17:00006y` 連續 56 輪 carried，從 BR 站 5 一路續推到終點站 0。
- 歸因：**官方列自己同段≥2 只有 71 段次、≥3 為 0；名冊是 1083／224** ⇒ 疊車不是上游或 ledger 帶進來的，
  是 reducer 端造出來的。
- 正式站此刻（10:20 那批 9 個快照）：車 129–134 台 vs 官方列 115–119 筆，每輪 1–4 段有 ≥3 台。
- 畫面症狀：一段軌道上三、四台車連在一起，其中只有一台有官方倒數撐腰（使用者原始回報的「重複的車」）。

### F3（P1）幽靈跑到終點站就停在那裡不動
- `coastForward:440` 的 `while (to !== dest …)`：到終點就不再推，之後只能等 `retireEpoch`（多半是 null）
  或停滯地板。而地板用的 `coastCycle` **只有物理下限、沒有上限**（`coastTiming:348-396`）。
- 實測：語料 `ov:2026-08-17:000042` 停在 BR `1>0`（`to===dest`）連 6 輪、到站時刻已過 227s，
  地板 = arr+372s；正式站 `ov:2026-08-17:0000ks` 停在 BR `22>23` **2572 秒（43 分鐘）**，
  它的地板是 3×870s＝43 分鐘（cycle 被灌成 870 秒／站，BR 實際約 104 秒／站）。
- 畫面症狀：文湖線／各線終點站永遠停著一台不動的車，好幾分鐘到數十分鐘才消失。

### F4（P1）斷訊恢復／自癒清掉的車，下一輪自己回到畫面
- 重排分支把未被官方確認的車放進 `dormant`（`roster:681-687`）；下一輪 dormant 進配對池
  （`roster:517-518`），配不到就走 `roster:675-695` 的 carried 分支被推回 `vehicles`（`689-691`）——
  因為「這條線這一輪不再是 realignLines」。
- 實測（`replay_deep.mjs` D4，對 BR 強制重排一次）：重排前 45 台 → 重排後畫 33 台、休眠 18 台；
  **下一輪那 18 台全部回到畫面，其中 12 台完全沒有官方列撐腰**。
- 畫面症狀：跳出「官方訊號恢復、已移除 N 台推估列車」之後 15–30 秒，被移除的重複車原封不動回來，
  通知的數字與畫面對不上。

### F5（P1）配對看到的位置 ≠ 畫面上的位置（routePosition 沒跟著續推更新）
- `coastForward` 不更新 `routePosition`（只在 `officialVehicle:423` 設定一次）。
  消費者：`physicallyReachable:176`、`pairCost:238`、群組 DP 排序 `roster:610`、`compareVehicles:494`。
- 實測 **43.0 台/輪（最多 55）** 的車，畫在 A 站、配對時被當成還在 B 站。
- 對照組（`ctrl_rpfix`，只補這一行）：脫鉤 43→0，但車數反而 191.9→194.8 ⇒ **這是一致性缺陷，不是疊車根因**，
  修它要連配對策略一起想。
- 畫面症狀：官方明明報了下一站的倒數，那台車卻沒有接上（跳到 F7 的「官方有列、畫面沒車」）。

### F6（P1）續推後的起點車仍掛 `terminal:true`，握有配對免檢通行證
- `physicallyReachable:189`：`if (prior.terminal && advance === 1) return true;`（不驗段秒）。
  續推後 `terminal` 沒有被改掉（`carried()` 只覆寫 from/to/arrEpoch），於是一台**已經被推離起點的幽靈**
  仍可無條件吃下下一段官方列的身分。
- 這種形狀的車正式站每輪 2 台、語料 264 台次（同 F1 的族群）。
- 畫面症狀：車號在兩台車之間跳；被搶走身分的真車當輪被丟掉（`ignoredObservations`）或另生一台。
- 信心：形狀已實測存在，**搶身分事件本身未逐一計數**（讀碼推論）。

### F7（P1）官方報了列、名冊沒有任何一台車在那附近
- `roster:643`：非起點的官方站間列配不到既有 ID 就 `ignoredObservations++` 丟掉。
- 實測（56 輪）：官方列沒有對應車 1200 筆，其中 **440 筆（7.9 筆/輪）同線同向 ±1 站內完全沒有車**；
  正式站此刻每輪 `ignoredObservations` 5 筆。
- 這正面牴觸「車子有官方數據就是在」。畫面症狀：某站牌顯示 3 分後有車，但那段軌道上一台車也沒有。
