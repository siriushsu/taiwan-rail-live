## 結論：推翻不了。核心算式逐 byte 重現，且新樣本獨立復現同一病徵。

### 1. 算式重現（10:17 那一輪，我方獨立實作）

```
trk:2026-08-17:hw:407  O_XINZHUANG dir1
eta {from:9,to:8,run:96,arrEpoch:1786933167} → arrSec 37167 → depSec 37071 (10:17:51)
bound key 20@33960>0@36817 → 站 9 表定發車 35460 (09:51:00)
identity = 37071 − 35460 = 1611 == payload.shift 1611   ✅
best fit  = 20@35580>0@38437 → 站 9 表定 37080 (10:18:00) → shift −9；次佳 +531   ✅
迴龍 terminal 列 arrSec=depSec=37324 (10:22:04) 綁 20@35580>0@38437 (tr[1]=35580) → 1744；
  best fit 20@37320>0@40117 → +4                                                   ✅
```
`identityOK` 對整份 payload 成立：10:17 輪 89/89、10:55 輪 87/87，零例外。

### 2. 我試過的四種「更簡單的解釋」，全部被證據擋掉

| 替代解釋 | 反證 |
|---|---|
| 這些車真的誤點 27 分 | **payloadShift − bestShift 全是班距整數倍**：276/552（BR）、540/1080/1620（新莊線）、480、1140…（見下方分佈）。真實誤點不會量化到班距倍數 |
| 班表過期／整體偏移 | 最佳擬合殘差中位 28 秒、最大 131 秒（10:17）；10:55 為 35／137。班表與現實吻合到秒級 |
| 時區／秒-epoch 單位錯 | 單位錯會在最佳擬合上留下同樣的常數偏移；殘差 ~0 且錯量各不相同（1611／1744／5401） |
| `run` 的語意被我誤用 | 拆開看：**非起點列**（81 筆）自己就有中位 27／最大 131 的殘差；起點列 run=0 完全不含任何行駛時間模型。兩邊各自成立，不互相依賴 |

`payloadShift − bestShift` 分佈（|Δ|>60 的 44 筆）：
180, 276×10, 300×2, 360×2, 420, 480×3, 540×9, 552×4, 1020, 1080×2, 1140×2, 1620×3, 1656, 1680, 1740, 2340

替代指派幾乎是一對一：89 個 claim 對應 88 個相異最佳班次，唯一碰撞在 BR
（文湖線本來就沒有逐站時刻表、是用班距推算的，見 `data/trtc_times.json` 的 source_notes）。

### 3. 最強的一條獨立證據：同一台實體車的自然對照組

| 時刻 | trackId | 方向 | 綁定 | shift |
|---|---|---|---|---|
| 10:17:40 | `trk:2026-08-17:hw:407` | dir1 | `20@33960>0@36817` | **1611** |
| 10:55:11 | `trk:2026-08-17:hw:407` | dir2 | `0@38820>20@41688` | **46** |

同一台 407，到終點轉向後被 destMismatch 驅逐重綁，shift 立刻回到 46 秒。
一台「誤點 1611 秒」的車不可能在 38 分鐘內把 26 分鐘追回來——這是「綁錯」而非「誤點」的直接反證，
而且它不依賴我對班表的任何解讀。同一輪 O_XINZHUANG dir1 群組仍卡在中位 1757。

### 4. 我唯一推翻掉的部分：因果句「迴龍 terminal 佔走了 407 該用的那一班」

事實部分成立（那一班確實被 terminal 列佔著），但**它不是操作性的成因**：

- 出生綁定有 cost cap：`cost=|shift−ref|>600` 直接丟掉（`trtc_board_ledger.mjs:1144`）。
  10:17 該群組的 shift 中位 ≈ **1708**（payload 代理值，n=4，範圍 1611–1744）⇒ 正確那一班的
  shift −9 的 cost ≈ 1717 **早就超 cap**，就算沒被佔走，出生綁定也綁不上去。
- 反過來說：1611 這條邊能存在，本身就證明當時 ref ≥ 1011（否則 1611 也會被 cap 掉）。
  真正在維持錯誤的是**群組 ref 鎖死**，不是單一 terminal 列的佔位。
- 另外沿用路徑（`:995`）**完全不重新評估班次**、也不過 cap，所以一旦錯了就靠慣性活著，
  當輪誰佔走哪一班對它沒有影響。

### 5. 風險與未確定點

1. **起點列語意**：memory `trtc-origin-identity-ghosts` 記著「官方起點列的進站時刻不是發車錨點」。
   若成立，範例 B（迴龍 1744→正確 4 秒）作為「這台車該綁哪一班」的證據要打折扣。
   但 ledger 自己就是拿它當發車錨點（`:987 scheduledEvent = tr[1]`），而且核心結論只靠 81 筆
   非起點列就成立，不受影響。
2. **沒有提修法，所以「修法會不會退掉別的」無從評估**。但先預警：把判準寫成「shift 應趨近 0」
   會同時撞到兩件事——(a) 真實誤點時它會把車硬拉回班表；(b) 使用者裁示「位置不用準、時間一定要準、
   不要每次打開都重算」，每輪重挑最佳班次＝重算，會直接違背。
3. `ref` 我只有 payload 代理值（同群組 shift 中位），不是 ledger 內部那個 20 分鐘窗的真值；
   cap 的量化結論方向明確但數字是近似。
