## 二、決定性反證實驗（判準與被測物不同源）

對每一筆官方錨點，掃**整份原始班表** `data/trtc_times.json` 同線、同終點、含同一 (from,to)
連續段的所有班次，算「官方到站秒 − 該班表定該段到站秒」，取最小絕對值＝**最佳可行差**。
被測物（後端 binder 選的那班）完全不參與這個計算。

四份快照合計：

- **站間錨點 286 筆：最佳可行差中位 +24 秒、p05 −111、p95 +114、|差|>300 秒 0 筆。**
- 起點列 41 筆（官方「下一班發車」vs 表定發車）：全部落在 −124～+137 秒。
- **同一批錨點，我們實際綁到那班的差：中位 +87 秒，|差|>300 秒 111/286＝39%。**

也就是說：官方資料顯示今天北捷**每一台車都在表定 ±2 分鐘內跑**（286/286），
但我們有四成的車被綁到 5 分鐘以上、最多 100 分鐘（`R_XBT` 6000 秒）之外的班次。
真誤點 19～29 分鐘的世界裡，不可能存在一班表定班次能對到 ±60 秒。

逐筆看更清楚——這是**整條方向的班次標籤整批平移 k 班**，不是雜訊：

```
G|2      我們選 0@37080 / 37380 / 37860 / 38280 / 38760
         最佳   0@37380 / 37860 / 38280 / 38760 / 39240   ← 整排剛好差 1 班（≈490s＝1×班距）
R|1      整排差 1 班（≈570s）
O_LUZHOU|1   整排差 2 班（≈1190s）
O_XINZHUANG|1 整排差 3 班（≈1750s＝3×580s）
```

另一條互相獨立的證據（我自己從 payload 讀的，非引用原稽核）：
`O_XINZHUANG` dir1 的**起點看板**（terminal 列）在 11:00:45 報下一班發車，
表定 11:00:00 ⇒ 起點只晚 45 秒。起點準點發車、線上的車卻被標成晚 29 分，兩者不能同時為真。

## 三、我試過但站不住的三種「更簡單解釋」

| 假說 | 檢定 | 結果 |
|---|---|---|
| 起點列（`terminal`）算法特殊造成的假象 | 把 terminal 與站間錨點分開統計 | **否**：站間錨點自己就有（O_XINZHUANG dir1 mid n=5 med=1736） |
| 班表那個方向整體偏移／缺班 | 掃全班表找最佳可行差 | **否**：每一筆都存在 ±137 秒內的同終點班次 |
| 該方向真的出事故／單向大延誤 | 20 分鐘四快照 + 起點看板 + 286/286 準點 | **否**：官方時刻全線準點，只有我們的標籤偏移 |
| 量測環境問題（頁面狀態、旗標、快取） | 全程 curl 原始 API、no-cache、不開瀏覽器 | **否**：現象在後端 payload 就已存在 |

## 四、對「修法」的保留（這部分我不同意照做）

提案：把「同線兩方向校正量中位數差 > 班距」做成 `evalLineAnomaly` 旁的具名哨兵。

1. **已量到的漏報（對稱偏移完全隱形）**：`BR` 四份快照兩方向中位＝375/323、369/365、419/358、
   195/364 ⇒ 方向差 52/4/61/169 秒，全部低於班距 276 秒 ⇒ **哨兵不會叫**；但同一批快照裡
   BR 兩個方向的「選到那班 vs 最佳可行」都差約一個班距（chosen 375 vs best 99）。
   偏移量 k 兩方向剛好相同時，這個哨兵結構上看不見。
2. **樣本稀疏的線根本評不了**：`R_XBT` 多份快照只有單一方向 1 筆（shift 6000 秒＝全資料最慘），
   方向差無定義 ⇒ 永遠不開火；`G_XBT` 每方向 n=1，中位數等於單點。
3. **「物理上不可能」是對持續現象成立，對單一快照不成立**：15 秒一輪、2 進 2 出＝30 秒遲滯，
   真事故初期單向大延誤是可能的。要用這個判準就必須加「持續 N 分鐘」條件。
4. **更好的判準已經在手上**：本節第二段那個「選到那班的差 vs 全班表最佳可行差」是直接量、
   與方向無關、不靠物理論證，且上面三個盲點全部沒有（BR、R_XBT、單快照都抓得到）。
   建議哨兵寫成「逐線 median(|chosen shift| − |best feasible shift|) > 門檻」。
5. **擺在 `evalLineAnomaly` 旁邊會誤傷語意**：`anomalyOf()` 驅動的是對使用者說
   「偵測到營運異常跡象（本站推定），位置僅供參考」（index.html:6348）與自家異常清單
   （18589/18592）——那是在指稱**捷運公司營運異常**。把「我們自己認車錯了」灌進那條通道，
   等於把自家 bug 對外講成北捷出事。這個哨兵應該走內部稽核／監控通道，不要進營運異常 UI。
6. **嚴重度提醒**：正式站現在 `TRTC_PURE_SCHEDULE_POSITION=true`（`OFFICIAL_ROSTER_ENABLED`
   預設 false），`metroLiveOn()` 對北捷線回 false ⇒ 這些 shift 目前**不會套進畫面位置**
   （index.html:16946、17148）。所以這是「官方名冊路徑（?officialroster=1）與車號標籤」的缺陷，
   不是今天使用者看得到的位置錯誤。哨兵的優先序要照這個現況定。
