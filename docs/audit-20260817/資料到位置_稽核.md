## F1（P0，已實測）純班表根本沒有純：`applyTrtcBoard` 繞過 `metroLiveOn` 直接寫 `_easedShift`

**證據鏈**

1. `metroShiftSec` 17313-17333：`on = metroLiveOn(ln)` 為 false ⇒ 17321 那行不執行 ⇒ **`target` 恆 0**。
2. `easedShift` 16774-16781：`target=0` 且沒有既存 entry ⇒ **fast path 直接 return 0、不建 entry**。
3. 但 `applyTrtcBoard` **17871-17873** 每輪對每台有 endpoint motion 的車做：
   ```
   const ek = trtcEasedMotionKey(ln, tr, physicalKey), old = _easedShift.get(ek);
   if (old) { old.cur = visualShift; old.sim = motionSec; old.at = performance.now(); }
   else _easedShift.set(ek, { cur: visualShift, ... });
   ```
   完全沒有 `metroLiveOn` / `TRTC_PURE_SCHEDULE_POSITION` 閘門。
4. `trtcEasedMotionKey` 16977-16980 產生的字串與 `metroShiftSec` 17318 的 `dch='track:'+physicalKey` **逐字相同**。
5. 於是 `easedShift` 走到 16788-16792 的有界衰減：`fall = adv × (maxRate−1)`，
   `maxRate = metroRateCap(ln)` 實測 1.33–1.38 ⇒ 每模擬秒只還 0.33–0.38 秒；
   而 `pollTrtcLive` 每 **15 秒**（18129）就把 `cur` 重設回 `visualShift`。⇒ **永遠回不到 0**。

**實測（10:22，`probe_shift`）** 9 線全部 `liveOn:false`、`anchored:0`，但：

| 線 | 在跑 | endpoint | shift 非零 | shift 範圍(s) | 位置偏離純班表(m) 中位/最大 |
|---|---|---|---|---|---|
| BR | 20 | 0 | 0 | 0 | 0 / 0 |
| R | 22 | 12 | 11 | −27 … +71 | 0 / **620** |
| G | 12 | 4 | 4 | 0 … +46 | 0 / 360 |
| O_XINZHUANG | 11 | 1 | 1 | −6 … 0 | 0 / 48 |
| O_LUZHOU | 8 | 2 | 3 | 0 … +39 | 0 / 374 |
| BL | 22 | 14 | 13 | −10 … +93 | 35 / **940** |
| Y | 8 | 2 | 2 | −328 … +55 | 0 / **770** |

**因果集合對照（`probe_causal`，102 台在跑）**：
`shift 非零且無 endpoint = 0 台`、`shift 非零且有 endpoint = 23 台`、
`23/23 都能在 _easedShift 找到 trtcEasedMotionKey(ln,tr,physicalKey) 這把 key`。
⇒ 非零校正的來源**只可能**是 17871-17873 那兩行。

**畫面症狀**：使用者看到的車不在班表位置上，最大偏 940 m（約兩個站間）。
而 8/17 上線的更新紀錄 **index.html:3839** 對外寫著「列車位置改用班表推估…位置是依班表推算的」——這句話目前是假的。

**修法**：17871-17873 加同一道閘門（`if (!TRTC_PURE_SCHEDULE_POSITION)`），
或更穩：`metroShiftSec` 在 `!on` 時直接 `return 0`，不進 `easedShift`（讓「關掉＝0」變成結構保證而不是資料狀態的巧合）。

## F4（P2，讀碼推論）`_trtcLastRendered` 造成的閉環：畫出來的位置回頭決定校正量

`freqTrainPosAt` 5304 把**畫出來的位置**寫進 `_trtcLastRendered`
→ `trtcBuildEndpointMotion` 17052-17058 讀它當 `startPos`
→ 17094-17111 由它算出 `remainingKm / requiredRate / endSec`
→ 17861-17862 `handoffSec = clamped==='high' ? motion.endSec : arrSec`；`visualShift = handoffSec − rawArrivalSec`
→ 17871-17873 寫回 `_easedShift`
→ `metroShiftSec` 讀回來改變位置。

`clamped==='high'` 時這個環才閉合（`visualShift` 依賴上一幀畫出的位置），
此時整條鏈**沒有任何外部錨點**，誤差會自我維持。
今日實測 `state._trtcBoardAudit.clampedHigh = 0`（`matched:73 / roster:103 / unreachable:18`），
所以現在沒閉環，但這是條件式的，不是結構上關掉的。

同一份 `_trtcLastRendered` 也是 `trtcHeadwayLinksForMotions` 17288-17292 算 `link.km` 的來源
⇒ L6 的限位量同樣踩在自己的輸出上。
