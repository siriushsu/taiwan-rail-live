# 北捷斷訊恢復後「幽靈車」根因診斷（2026-08-15）

## 結論摘要

1. 根因在身分層，不在缺訊退場：無號端點列沒有「同一發車 occurrence」鍵，只在 `line|dir` 全線做保序配對。
2. `arrEpoch` 又同時參與 rollover 拒配與配對成本；端點 ETA 每輪變、無號列集合也每輪變時，舊端點 ID 會被別列拿走，當輪端點列遂再次出生。
3. reducer 不做相同 row 去重；每個未配到的 terminal row 都各配一個新 ID。單一 reducer row 一次最多生一台，但同一來源 frame 也可被 worker 重跑。
4. 07:44 的 004u/v/w、004x/y/z 證明「同一 birth signature 多 ID」；現有資料缺 07:26 原始 frame，尚不能唯一分出多筆上游 row 與同 frame 多次 reduce。
5. 07:44 原始 `board` 只有一筆 R dir2 起點列；加兩筆相同 raw row 仍被合成一筆。這否定「上游 duplicate 是唯一解」，但不能反推 07:26 的 raw multiplicity。
6. `hardNoMatches=44` 是 44 筆「唯一官方號碼硬配成功」，不是 44 筆失敗；`unclaimed=133` 是位置 claim 前置拒收，也不是身分失配數。
7. outage 兩輪只餵入 Y 的 9 筆 reducer rows，北捷舊車被 carry；恢復才重新出現可出生的北捷 terminal rows，首台仍堆著的異常端點車 birth 是 07:01:02。
8. 抽取 `index.html` 真函式重放：35/35 端點車在 `arrEpoch+1` 都出站；07:44 當秒 35 台仍可見、13 台正在站間，13 台全是無號路線牌。
9. 最小修法是同時做：同 frame 冪等、完全相同 reducer row 合併、端點 occurrence 專用配對；不可加入任何時間退場。

## 逐題答案

### 1. 端點列用什麼鍵配對；為什麼 ETA 滑動會另生

目前沒有端點專用的穩定鍵。流程是：

- 有且只有一筆同號 row 時，先用 `line + dir + officialNo` 找唯一 prior，仍須通過物理可達閘門（`scripts/trtc_official_roster.mjs:369-400`）。端點列實例多為空號，所以走不到這層。
- 其餘 row 只用 `groupKey = line|dir` 分組（同檔 `:97-99`），在全線以 route position 排序後做最大配對數優先、成本次之的保序 DP（`:177-215,402-416`）。成本依 timeline 相同 leg 的 ETA 差、位置、目的地與 `arrEpoch` 差，不是端點 occurrence ID（`:165-185`）。
- `terminalOccurrenceRolled()` 另把「prior terminal 的 `arrEpoch <= now`、current 同端點 `arrEpoch > now`」直接判成不能配，視為下一趟（`:121-126,157-162`）。除此以外，terminal 與後續第一段也只參與全線 DP。

因此 `arrEpoch` 每 15 秒修訂時，身分證據本身也在變。只要先前端點 ID 在全線 DP 中被另一筆前進 row 使用、同端點候選因 rollover 被拒、或相同 frame/相同 terminal row 再次進 reducer 而沒有可用 prior，該 terminal index 就落到出生迴圈；正常營運下非 terminal 會被忽略，但 terminal 無條件有生車權（`:418-426`）。這就是「滑動 row 被當成新 occurrence」的直接程式機制。

fixture 佐證：07:44 R dir2 的 0044、0046、004c birth 分別為 07:18:32、07:18:47、07:19:32；0049/004a/004b/004c 更曾以同一端點 birth signature 出生，之後分別被配到 10→11、12→13、13→14，僅 004c 留在端點（`fixtures/trtc-outage-20260815/postrecovery_0744.json:1`）。這證明「某個端點 ID 被後續沿線 row 拿去」和「同 birth signature 留下多個 ID」兩件事同時發生。

### 2. 輪內去重、單 row 生車上限、三胞胎判定

reducer **沒有輪內相同 row 去重**。`canonicalRows()` 把每筆都 normalize/sort，對相同 `rowKey` 只加 `occurrence=0,1,2...`，沒有刪除（`scripts/trtc_official_roster.mjs:71-95`）；既有測試也明示兩筆完全相同 reducer rows 在 cold start 會留下兩台，而不是合一（`scripts/verify_trtc_official_roster.mjs:203-206,391-395`）。

一筆 reducer input row 在單次呼叫中最多生一台：`assigned` 以 row index 為鍵，每個未配 terminal index 只呼叫一次 `allocateVehicleId()`（`scripts/trtc_official_roster.mjs:374-376,418-426`），建車迴圈也每 index 最多 push 一台（`:428-442`）。scratch 實測一筆得 1 birth，三筆完全相同得 3 births（`scratch-codex/analyze-roster.mjs:69-76,122-126`）。上游 raw row 的正常管線也不會一拆多：`resolveBoardRows()` 每 raw 最多 push 一筆（`scripts/trtc_board_ledger.mjs:187-225`），後續 `collapseClaims()` 只合併/刪除（`:341-377`），`attachOfficialTimelines()` 是一對一 map（`:383-432`）。

但「三胞胎唯一只能是上游同輪送三筆」**不能由現有資料定案**，因為 worker 允許相同 `sourceRevision + sourceFrameKey` 在較晚 acquisition 再次 reduce：只有舊 state 的 `sourceObservedEpoch` 較大，或 acquisition 完全相同且 frame order 不小於新值時才短路；較晚 request 會落到 `trtcOfficialRosterSnapshot()` 再跑 reducer（`worker.js:1274-1304`）。現有 verifier 還把「同內容、較晚觀測會再寫一次 freshness barrier」列為綠燈契約，實際驗證 `writes===1`（`scripts/verify_trtc_official_worker.mjs:190-198`）。故三胞胎有兩個仍成立的來源：

1. 單次 reducer 收到三筆相同 terminal rows；或
2. 同一上游 frame 被三次 production request/CAS 重跑，每次又因端點配對失去候選而生一台。

既有證據證明第 2 項在架構上可發生，也證明第 1 項不是唯一解：07:44 的 raw `board`（worker 對合法 TrackInfo row 一對一搬運，`worker.js:847-860`）只有一筆「象山→淡水」R dir2 起點 row；在完整 07:44 raw board 中額外複製兩筆，重跑 resolve→claim→collapse 仍是 101 rows、R dir2 起點仍一筆（`scratch-codex/analyze-roster.mjs:35-50,102-126`）。不過缺少 07:26:33/48 當刻 raw frame 與每次 CAS input，所以不能把第 1 項歷史上完全排除，也不能證明第 2 項當時確實造成每一個 sibling。

可唯一分辨的最小實驗：同一個 15 秒 revision 同時保存 (a) raw `TrackInfo`/現有一對一 `board` 的端點完全相同 row 數，(b) 進 reducer 的 canonical `rowKey + occurrence` 數，(c) 每次 CAS 的 `sourceRevision/sourceFrameKey/sourceObservedEpoch/birth vehicleId`。若 raw/canonical 都只有 1，而同 signature birth ≥2，就是第 2 項；若單次 canonical 已有 3，才是第 1 項。現有 rounds 已在 births 停止後才開始，不能補回 07:26 的缺口。

### 3. 真正發車 row 為何沒有接回端點車

配對是「每個 current row 與每個 prior vehicle 都只可用一次」（`assigned/usedIds`，`scripts/trtc_official_roster.mjs:374-416`），但端點無號車沒有 origin occurrence alias。真正的 0→1 row 只能和所有同 `line|dir`、物理上可達的 prior 一起進保序 DP；重疊 timeline ETA、位置與排序決定它拿到哪個 ID（`:128-215`），不保證拿到語意上那一班端點 ID。已有多台端點 duplicate 時，一筆發車 row 最多帶走一台，其餘全部走 carry（`:444-454`）；若前進所需段秒不可能在兩輪觀測時間內完成，`physicallyReachable()` 會拒配（`:128-155`），未配到的站間 row 又依法不得 birth（`:421-423`）。下一筆未配 terminal row 卻仍可 birth，於是形成「前進列忽略/接錯 + 端點再生 + 舊車繼續 carry」的單向累積。

07:44 audit 應正確解讀為：101 current rows 中 90 accepted/matched、11 個未配非 terminal 被忽略、39 台 prior 未被使用而 carry，合計 129 台；`hardNoMatches=44` 是 44 筆唯一官方號碼硬配成功（變數遞增點在 `scripts/trtc_official_roster.mjs:396-400`），不是 hard-no-match 失敗。`dropped.unclaimed=133` 是 `claimBoardRows()` 對倒數尚遠於 `run+dwell` 或無 run 的 raw rows 前置拒收（`scripts/trtc_board_ledger.mjs:254-274`）；`collapsed=17` 是 claims 合併差額（`worker.js:1423-1429`）。兩者會減少可用 timeline/身分證據，但不能當成 reducer 失配筆數。

### 4. 端點疊車會不會變成路線幽靈

會。`trtcOfficialVehiclePosition()` 在 timeline 沒有 moving segment 且 `from===to` 時，必走 `trtcOfficialDeparturePosition()`（`index.html:4783-4795`）；該函式在 `arrEpoch` 前停起點，之後取 `departureRun`/固定第一段秒並插值，抵第一站後再交給 coast（`:4726-4743`）。`trtcOfficialCoastPosition()` 逐段用固定 run+25 秒停站推到已知 dest 才回 null（`:4687-4724`）。reducer 又會為一般線 terminal 車填 `departureRun`，但 `retireEpoch` 在沒有真正終點 timeline 時保持 null（`scripts/trtc_official_roster.mjs:276-300`）。

`scratch-codex/replay-frontend.mjs` 直接從 `index.html` 抽取上述真函式、載入 07:44 的 35 台 `terminal && from===to && timeline.length===1` 實車（抽取與選樣在 `:11-54`，實際代入與統計在 `:56-84`）：35/35 在各自 `arrEpoch+1` 已離站；07:44 當秒 35/35 都仍有位置、13 台正在站間，這 13 台全部 `officialNo=null`，即路線縮寫橢圓牌幽靈。004u/v/w 在同秒得到完全相同位置，004x/y/z 亦然。所以端點疊車確實會經 departure/coast 轉成沿線同行幽靈；這不是推測。

### 5. 為什麼恢復後才開始

實際 outage fixtures 並非 worker 的 `feedMode=outage` 分支，而是 TrackInfo 當輪只剩另一上游的 Y：06:49/06:52 的 legacy board 各 23/25 rows，reducer 都只有 9 rows、births=0、carry=70/68（`fixtures/trtc-outage-20260815/outage_0649.json:1`、`outage_0652.json:1`）。對沒有 current group 的北捷 prior，reducer 不清 state，只在已知 `retireEpoch` 到時才退場，否則 `carriedVehicle()` 原樣保留（`scripts/trtc_official_roster.mjs:336-347,444-454`）。若 TrackInfo request 真失敗，worker 更直接讀 D1 held payload、不呼叫 reducer（`worker.js:1196-1221,1359-1362`）。兩路都沒有「33 分鐘後重置/冷啟動」。

恢復 full TrackInfo 後才重新出現北捷 terminal current rows；所有未配 terminal 都可進出生迴圈，而 33 分鐘 carry 下來的舊車也仍在候選池。`recovered_0701.json` 這一拍 audit 雖為 births=0（它是出生之後的下一次同 revision/後續寫入），名冊內仍可看到 R dir2 000032 的 birthEvidence=`observedEpoch 1786748462`＝07:01:02、起點 future arr=07:09:51；到 07:44 它仍是 terminal 且 retireEpoch null（兩 fixture 均為 `:1`）。因此恢復是「重新打開 terminal 生車入口」，不是 timeout 到期；其後每次無號配對失穩/同 frame 重跑都可再加車，而 carry 契約保證錯生車不會因缺訊或年齡被清掉。

### 6. 最小修法方向

見下一節。核心不是刪舊車，而是讓同一份官方出生證據只能建立一個仍可追蹤的 occurrence。

## 最小修法建議

建議三個都做；只做其中一個不足以同時封住同輪 duplicate、同 frame 重跑與跨輪 ETA 滑動：

1. **worker 同 frame 對 reducer 冪等（最小且必做）**：在 `trtcPersistOfficialRoster()` 讀到相同 `sourceRevision` 且 `sourceFrameKey` 完全相等時，禁止再呼叫 `trtcOfficialRosterSnapshot()`；若較晚 `sourceObservedEpoch` 仍需充當 freshness barrier，只 CAS 更新 observation/order metadata，`vehicles/rows/nextSequence/diagnostics` 原封不動。位置：`worker.js:1274-1304`。不能單純「直接 return 且不更新 barrier」，否則 verifier 的 1002 同 frame 不能擋住隨後才到的 1001 異 frame（`scripts/verify_trtc_official_worker.mjs:190-198`）。同秒但內容不同仍照現行 frameKey/frameOrder 規則 reduce；這不改出生、退場契約，只消除同一證據重放。
2. **完全相同 reducer row 合一（fail closed）**：`canonicalRows()` 以既有 `rowKey()` coalesce 完全相同列，不再用 `occurrence` 把不可區分的證據刻意變成多台；另記 `duplicateRowsCollapsed` 診斷。位置：`scripts/trtc_official_roster.mjs:71-95`。若上游三班真的連 line/dir/origin/dest/ETA/no/timeline 全相同，現有證據本來就無法證明是三個身分，顯示一台比製造三個幽靈安全。
3. **端點 occurrence 專用配對，先於全線 DP**：在 `reduceOfficialRoster()` 的 hard-number/一般 `alignOrdered()` 之前，先處理 `(line,dir,origin)` bucket；第一段 `origin→origin+step` 要優先消耗同 origin 的 pending terminal ID，其餘 terminal ETA 修訂優先接回尚未消耗的 pending ID。只有「current terminal occurrence 數大於可用 pending ID」，或既有 pending 已由第一段官方 row 明確帶離起點時才 birth；不得只因 `arrEpoch` 每輪滑動改 ID。位置：`scripts/trtc_official_roster.mjs:121-215,380-426`。`dest` 不可進 identity key（契約允許目的地修訂）。

重放驗收使用現有 fixtures，不需網路：

- 逐檔把 legacy `board` 還原成 raw TrackInfo 形狀，跑 `resolveBoardRows→claimBoardRows→collapseClaims→attachOfficialTimelines→reduceOfficialRoster`；07:44 可精確重現 `297 resolved / 118 claims / 133 unclaimed / 101 collapsed`（`scratch-codex/analyze-roster.mjs:25-50,102-121`），證明 harness 與 production audit 對齊。
- 同一 frame 連續餵 3 次、再把每個端點 raw row 複製 3 份：每個完全相同 birth signature 最多一個 ID、第二/三次 reduce births=0、`nextSequence` 不動；把 frame 內非端點欄位 shuffle 也必須同結果。
- 依 `outage_0649→outage_0652→recovered_0701→postrecovery_*→rounds/*` 重放：outage 不得因空窗/資料齡刪任何未到已知終點的 prior；恢復不得讓 `(line,dir,origin,birth signature)` 基數累增；非 terminal 未配列仍不得 birth。
- 加 endpoint handoff 合成 gate：terminal ETA 每 15 秒滑動 20 輪仍同 ID；出現第一段 row 時該 ID 前進；同時另有下一個 terminal occurrence 時才精確 +1 ID。反向仍必須新 ID、目的地修訂不換 ID、終點抵達才收車。
- 最後重跑抽取式前端腳本；修後 roster 不應再有相同 birth signature 多 ID，因而不會有同秒同軌的多胞胎路線牌。保留現有「缺訊不退場／只到終點退場」mutation gates（`scripts/verify_trtc_official_roster.mjs:628-655`）。

本次離線診斷已實跑 `node scratch-codex/analyze-roster.mjs`、`node scratch-codex/replay-frontend.mjs` 與既有 `node scripts/verify_trtc_official_worker.mjs`；三者均正常結束。既有 worker verifier 全綠不是「沒有 bug」：它目前明確要求同內容較晚 observation 再寫 freshness barrier，以及 duplicate occurrence 一 row 一 ID（`scripts/verify_trtc_official_worker.mjs:190-198,213-227`）。修法應保留前者的 ordering barrier，但拿掉同 frame 重跑 reducer，以及不可區分 duplicate 的「一列一 ID」。

## 風險與未確定點

- 缺 07:18～07:27 每 15 秒的 raw TrackInfo、collapsed reducer inputs 與 D1 CAS 嘗試紀錄，故無法把三胞胎唯一歸因為「單 frame 三 raw rows」或「同 frame 多次 reduce」。上文已給最小可判別採樣。
- 現有 `birthEvidence` 沒記 `dest/sourceNo/row occurrence/sourceFrameKey/sourceObservedEpoch`，多個不同原始列可投影成相同 signature；不能從 07:44 最終 roster 逆推出 07:26 raw multiplicity。
- `hardNoMatches` 命名極易誤讀；它實際是 hard-number 成功數。修正觀測欄名雖有助日後診斷，但不是本次最小功能修法。
- fixtures 的 R dir2 `from=0,dest=26` 依 `data/trtc.json` 實為象山→淡水，不是「站 0 淡水」；不影響端點疊車/身分根因，但報表標站名時應按本地模型站序。
- 端點 occurrence 配對若只做「同 origin 永遠接回」會漏掉真正下一班；必須以第一段官方 row 消耗 pending token，並用 current occurrence 基數判斷新增，不能以任意 timeout 代替。
