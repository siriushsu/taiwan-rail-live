# 捷運雙軌左右：真值、量法與修正（2026-09-09）

使用者回報「捷運雙軌的方向，現在似乎蠻多路線是跟真實的方向相反的」，接著補了一句
「北捷全都是右向通行」。實測下來 18 條線裡有 15 條指反了。

## 一、真值不取自本專案

兩個互相獨立、都不經過本專案任何資料的來源：

1. **OSM 的 `type=route` 關聯**：每條線往返各一條，成員 way 依行進順序排列。把往返兩條各自
   縫成一條折線，在其中一條上每隔一段取切線，量另一條落在左手邊還是右手邊。
   靠右行駛 ⇒ 對向股道在左。逐線結果（`https://api.openstreetmap.org/api/0.6/relation/<id>/full.json`）：

2. **高雄的 `oneway=yes` 節點順序**：高捷的股道在 OSM 有單向標記，可以直接從節點順序讀出
   行車方向，不必經過關聯。紅線 274 個取樣點、環狀輕軌 1254 個取樣點，兩條都靠右。

三鶯線在 OSM 還沒有 route 關聯，沒有獨立真值；它與其餘 17 條一致採靠右。

## 二、修正前的實況

`npm run check-metro-track-side` 對修正前的封包跑出來：15 條線整條指反（對向股道被畫在右手邊），
高雄環狀輕軌是唯一整條正確的，高雄紅線是 24 個區間裡南段 5 個指反、北段 19 個正確。

根因在 `scripts/build_metro_physical_routes.mjs` 的候選成本：

```
cost: p.lengthM*.001 - side
```

`side` 為正代表候選股道在行進方向的左手邊；減號讓 side 越大越便宜，於是每條線都被指到左邊那條。
高雄兩條線因為來源有 `oneway` 標記把路徑限住了，才沒有整條跟著歪。

## 三、修正

1. 建置端改成 `cost: p.lengthM*.001 + side`（偏右）。
2. 當初餵給建置端的 `.cache/physical-tracks/*` 已經不在本機，所以同一個修正由
   `scripts/fix_metro_track_side.mjs` 直接對封包重做一次。它自己量、自己判斷，
   重跑不會再翻回去（實測兩次輸出的 md5 相同）。
3. 翻面時**只換 path 的內容，不動 routes 的 pathIds**。索引是外部資料認得的東西——
   `scripts/fixtures/physical-taipei-0908.json` 直接存 pathIds——重編會讓那個固定樣本
   指到別條股道；就地換內容也不會留下一批沒人引用的孤兒 path。
4. 高雄紅線南段翻面後，凱旋—獅甲那個區間的接縫對不上：來源在那裡本來就讓兩個方向
   互相跨到對方股道。該區間改成沿同一條 way 直走，整條線的股道歸屬才一致。

## 四、量法上兩個會騙人的地方

- **來源只畫一條中心線的區間**（台中綠線北屯總站—四維國小、支線）兩個方向拿到的是
  同一批座標。最近點會落在自己前後方，量到的「左右」純粹是重新取樣的位移造成的雜訊，
  而且會隨曲率翻號。判準因此要求橫向分量至少 1.5 m——雙軌中心距不會小於 3 m。
  沒有這一條時台中綠線會停在「81% 對向在左」的混合狀態。
- **原始節點疏密不均**。短區間只用原節點取樣會只剩幾個點，結論會跟著單一個轉彎跑。
  兩支腳本都先重新取樣（修正腳本 10 m，驗收腳本沿用原節點但每兩點取一點）。

## 六、順帶修掉的一個外洩

`route-runtime.js` 會把展開後的線形記在 way 上當執行期快取（`sourcePath` 的 `w._path`）。
先前的 `extend_guangci_physical.mjs` 把它一起寫回了檔案，封包裡留著 8 份重複座標；
我自己第一版腳本更寫進 644 份、檔案從 1.34 MB 漲到 1.94 MB。現在寫檔前一律清掉，
封包反而比原本小了 6.7 KB。
