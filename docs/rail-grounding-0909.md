# 軌道貼地與低角度跟車修正 — 2026-09-09

## 原因與修正

- 舊層位產生器把正 layer 當成橋梁，整段以 layer × 8m 作初值；其中 190 條未有 bridge 標記的地面 way 被加上橋墩（另外 3 條有明示隧道，仍保留地下判定）。新分類將結構種類與交叉上下序分離：只有明示 bridge 的線形可以繪製橋梁，正 layer 仍用來約束交叉順序，地面高度初值改為 0。
- 起伏模式原固定 DEM 剖面含全線至少 2.5m 淨空，不能拿來當作路基高度。實體軌道、逐節車體、跟車鏡頭改為共用畫面地表加層位差。一般地面段只有 0.65m 軌面顯示餘量；交叉、橋隧及必要銜接坡道保留。
- 桌面 3D 跟車原走整列取景，低角度會把車頭擠出畫面。桌面 3D 在 60° 以上改以第一節車廂為取景目標，保留桌面拖曳解鎖的既有操作；手機／放空仍使用原本的嚴格車頭鎖定。
- 平原號等示意列車未綁定班表股道，先前會畫在高架下。只借用同系統、原位置 3m 內、方向誤差小於 15° 的線形高度，若相近候選層位有歧義則拒絕；不改動列車 XY、班表或派軌。兩個方向共用規則。
- 高架尺寸與層位間距仍為示意，沒有宣稱完成全台橋梁工程模型或測量標高。沒有明確橋梁資料的路段先回地面。

## 來源依據

[OSM layer](https://wiki.openstreetmap.org/wiki/Key:layer) 僅表示交會處上下序，不代表高度或橋梁；[bridge](https://wiki.openstreetmap.org/wiki/Key:bridge) 與 [embankment](https://wiki.openstreetmap.org/wiki/Key:embankment) 為不同結構。採用目前版控的來源標記，未重新抓取或改寫軌道平面線形。

## 官方橋隧幾何補正（同日第二輪）

### 為什麼還要補

上一輪把「正 layer 當橋梁」的誤判修掉之後，剩下相反方向的缺口：**來源沒有標記、實際
卻是結構的路段**。高鐵有 8% 線長被 OSM 標成地面（官方只有 1%），臺中捷運綠線整條全高架
卻有兩段沒標。那些缺口讓連續高架中間憑空落地，跟「一般路段貼地」是兩件不同的事。

### 來源

內政部國土測繪中心「臺灣鐵路」「高速鐵路」「捷運」三份 Shapefile（政府資料開放平臺
[73220](https://data.gov.tw/dataset/73220)／[73221](https://data.gov.tw/dataset/73221)／
[73222](https://data.gov.tw/dataset/73222)）。逐路段切分並標記結構種類，臺鐵那份另有
橋隧專名（855 段具名）。授權為政府資料開放授權條款第 1 版，條款原文授權「不限目的、
時間及地域、非專屬、不可撤回、免授權金」利用，並明列「包括但不限於開發各種產品或服務
型態之衍生物」，義務只有顯名。與 OSM 的 ODbL 不同源，故不混寫進 network.json，
另存 `data/rail_structures_official.json` 對照表。

結構種類碼官方沒有附字典，`1=橋樑 2=平面 3=地下 4=山岳隧道` 是用幾何交叉驗證出來的：
捷運那份板南線與松山新店線 100% 落在 3、文湖線 96% 落在 1，與「全地下」「全高架」的
事實吻合。這一條是推論不是官方文件，寫在 `scripts/build_rail_structures_official.mjs` 檔頭。

### 對正式站驗收才現形的顯示缺陷

六支瀏覽器驗收對 `BASE_URL=https://railisland.tw/` 重跑，四支綠、兩支紅。追下去發現的不是
判準過期，是**產品缺陷**：

- **現象**：地形圖磚晚於結構幾何抵達時，橋面與橋墩會停在 0m，而該處地形是 11~12m
  ⇒ 整段高架橋被埋進地形裡，25 秒內不會自己恢復。WebKit 必現，Chromium 因為 DEM 載得快
  而躲過。本機完全照不到——DEM 在磁碟上，結構永遠一次就建在正確高程。
- **根因**：`map3d.js` 那條「地形到貨就重建」的監聽寫成 `sourceDataType==='content'`，
  但圖磚到貨事件帶的是 `e.tile`、`sourceDataType` 是 undefined（只有 metadata／visibility
  才有值）。實測 chromium 正式站／webkit 正式站／webkit 本機三個環境的 content 事件都是 **0 次**，
  那條監聽從寫下來就是死的。
- **修法**：監聽條件改收 `e.tile`；另外在建置時記下當時的地面高程，之後高程變動 >0.5m 一樣重建
  （單一到貨事件可能早於整片 DEM 到齊）。
- **突變測試**：用 6 秒 DEM 延遲在本機重現。還原修法 ⇒ `routeBuilds` 停在 2、60 個取樣點全埋；
  補回修法 ⇒ `routeBuilds` 2→4、貼合 60/60。正式站 WebKit 部署後複驗 `gzero 0 / consistent 60`，
  截圖看到橋墩與橋面正常。

### 兩支驗收腳本原本照不到它

- `verify_rail_structures_browser`：桌面寬度走 `renderer.setGroundMode` 捷徑，那不是使用者的路徑
  （手機分支按的是真的控制項，所以手機四個寬度在正式站是綠的）。已統一成兩邊都按同一顆控制項。
- 同一支的 terrain 判準是**同源自洽**：比對「建出來的 groundM」與「當下查到的高程」，兩者在
  DEM 未載入時都是 0 ⇒ 恆真。實測把控制項固定按 flat，整列照樣全綠。已補正向對照
  （地形真的開著、DEM 在取樣點真的有值），突變後兩個引擎都紅。
- `verify_rail_grounding_browser`：模型等待 45s→90s。45 秒是照本機磁碟調的，對正式站
  webkit 會偶發等不到兩節模型（三次跑有兩次）。放寬只是晚一點宣告失敗，判準沒放水。

### 對正式站跑瀏覽器驗收本身會間歇紅

`verify_rail_grounding_browser` 對 `https://railisland.tw/` 跑了五次：三次在 webkit 某個寬度
的模型等待逾時（375／375／414，每次不同）、一次兩個引擎都卡在 `#tabMore` 的 tap、一次 36/36 全過。
同一支對本機 dev server 連跑都是 36/36。**每一次紅都落在 Playwright 的等待或點擊動作上，
沒有任何一條判準真的失敗**——印出來的每一列都是 true。單獨跑那個模型等待，6 秒內就到 2。

所以「對正式站重跑」要當成有雜訊的量測：紅了先看是判準紅還是動作逾時，後者重跑即可，
不要為了讓它綠而放寬判準。真正只有對正式站才照得到的是**資產下載時序**那一類缺陷
（本節前面那個橋被埋住的就是），那類紅會穩定重現、而且兩個引擎的行為不同。
