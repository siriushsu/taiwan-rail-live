# 橋隧判定與顯示高度（issue #57，v0911b）

回報者 iceman0623 在 v0910g 跟著高鐵 0120 次（左營→南港）走到 **24.2738, 120.6643 z20**，
說「高鐵軌道沒有整段多次上上下下的，似乎是把過山洞模擬成進入地下道，變成一下橋樑一下地下道」。

那個視角上的兩條 way 都落在下面第一個根因裡。但這不是高鐵專屬的缺陷——三個根因全網路都有，
台鐵、高鐵、各捷運與輕軌都中。

## 三個獨立的根因

### A. 來源與官方互指時，只准往一個方向改判

`build_rail_structures_official.mjs` 舊規則只補「來源沒有標記」的地面段：來源明示 tunnel、
官方橋隧圖資說是橋梁時，它直接 `continue`，連爭議記錄都不寫。

回報者假設的極性是反的。實際數：

| 方向 | 條數 | 分佈 |
|---|---:|---|
| 來源 tunnel、官方 bridge | 13 | 高鐵 6、台中捷運 5、機捷 2 |
| 來源 bridge、官方 tunnel | 1 | — |

13 比 1，值得開放反向改判。改法不是無條件相信官方，而是加第三個獨立來源裁決：
用 DEM 地形起伏（`reliefM`）判斷那一段是不是真的在山體裡。改判過的條目帶
`officialOverride` 與 `officialReliefM`，`structure-kind.js` 只有看到 `override` 才准推翻來源明示的標記。

回報者視角上的 103397339 與 103397328 兩條在這 13 條裡，`verify_rail_structure_heights.mjs`
的 G1 對這兩條寫了具名回歸。

### B. `layer` 的數值被當成顯示高度

`rank` 本來只拿來排相交上下序，卻被乘上 8 公尺當層位。OSM 把高鐵某些高架橋標到 `layer=4`，
乘出來就是離地 32 公尺的空中軌道；全網最高到 **48 公尺**。改成只取結構種類的正負號之後，
橋面離地最高 **12.1 公尺**。

G2 拿舊規則當正向對照：同一份資料用 `rank×8` 重算，量到 48 公尺才算對照有效。

### C. 隧道的初始深度把洞口兩側的高架橋拖下去

隧道端點會沿用相接股道的顯示高度，但相接的那條高架橋反過來又被隧道的初值拉低，
於是每一個洞口旁邊的高架橋都在洞口處俯衝。修改前 204 處洞口銜接有 180 處俯衝超過 3 公尺，
最深 16 公尺；修改後最深 **0.92 公尺**。

G3 量的是「同一條高架橋自己在離洞口 200 公尺處的高度」對「洞口處的高度」的落差——
比較對象是同一條線自己，不是實作算出來的期望值。真正要上橋的引道（洞口另一端接的是橋梁）
另計為 `ramps`，不進俯衝分母。

分母的普查（2026-09-11 實測）：586 個山岳隧道洞口端點、614 個相鄰段，
扣掉鄰段也是隧道的 250 筆、上橋引道 134 筆、太短無法比對的 60 筆，
實際列入判準 **170 筆**（高架 136、平面 34）。這個 170 有具名下限斷言（150），
分母無聲縮水時判準會自己紅，不會變成恆綠。

把同一支閘門直接跑在修改前那棵樹上（`tunnel-base-0911`），G1 對回報者視角的兩條 way
各自報「高架橋不該有負的離地高度，最低 −16.0m」——回報者看到的就是這個。

## 第四個缺陷：山坡表面浮出軌道的痕跡

做截圖時才看到的：`live-underground-3d` 會 `clearDepth()` 讓地下段看得穿地表，
於是埋在山體裡的隧道被畫到山坡表面上。改成用**局部覆土深度**（地表高程減顯示高度）決定，
覆土 ≤30 公尺才穿透。

不能用隧道段的 `boreKind`（整條 run 的山岳／地下分類）當判準：台鐵台北地下段一路接到南港丘陵，
整條 run 的地形起伏 54.6 公尺會被判成山岳隧道，但它的中位覆土只有 12.2 公尺——
拿 run 級判準會把台北地下段的透視砍掉 14%。改成局部覆土之後，台北的透視取樣點仍有 96.1% 穿得過地表
（13158 → 12751 段），而覆土超過 100 公尺的取樣點 0 個穿透。

## 新的守門人：`verify_rail_structure_heights.mjs`

既有四道閘門對這三個缺陷全部是綠的：`verify_rail_levels` 驗相鄰 offset 差與交會淨距，
橋面離地 40 公尺完全合法；`verify_rail_tunnel_grade` 驗隧道**內部**的縱坡，
而隧道一旦被誤判成橋就整個退出它的分母——缺陷會讓判準的樣本自己消失；
`verify_rail_grounding` 驗的是「有沒有多長出橋墩」，方向相反。

| 閘門 | 量什麼 | 期望值來源 | 現值 |
|---|---|---|---|
| G1 | 反向改判生效且每條都有地形證據 | `rail_structures_official.json` ＋ DEM 起伏 | 13 條，含 103397339／103397328 具名回歸 |
| G2 | 橋面離地高度 | 正向對照＝舊規則 `rank×8` | 最高 12.1 m（對照組 48 m） |
| G3 | 洞口銜接處的俯衝 | 同一條高架自己離洞口 200 m 處的高度 | 最深 0.92 m（對照組合成俯衝 7.8 m） |
| G4 | 隧道分類分母不得無聲縮水 | 具名斷言 | subsurface 423／mountain 293 |
| G5 | 地表穿透門檻 | 從實作檔讀回 `SEE_THROUGH_COVER_M`，雙向斷言 | 門檻 30 m、捷運仍穿透 96.1%、深層穿透 0 |

G3 另外對「量到幾處洞口銜接」寫了具名下限（150，2026-09-11 基準 170），
避免分母縮水時判準自己失明。

已掛進 `ship_web.mjs` preflight，單獨重跑 `npm run check-rail-structure-heights`；
盤點表 `npm run check-tunnel-grade-stats`（吃一個參數＝另一棵樹的路徑，做修改前後對照）。

## 順帶做的兩件事

### 軌道不再是一塊棕色的板子

道碴改梯形斷面（頂 3.4 公尺、底 4.6 公尺），z17 以上長出鋼軌、z18.5 以上長出枕木。
分級在 `map3d.js` 的 `detailLevel()`。

枕木間距是從**畫面**量的，不是從實作的常數讀回來的：z21、pitch 0 的正射截圖
（`output/tunnel-compare/track-overhead.png`）轉正後，兩條鋼軌中心距 63 px＝軌距 1.435 公尺
⇒ 43.9 px/公尺；沿軌道方向的自相關主峰在 **29 px**＝0.66 公尺，對得上 `TIE_SPACING=.65`。

### 隧道口長出拱圈

斷面比例沿用 `prototypes/taiwan-3d/rail-occlusion.js`：拱心半徑 3.2 公尺、起拱線在軌頂上 2.6 公尺、
洞底在軌頂下 1.2 公尺、石環厚 0.7 公尺。

洞口位置在建置端算好隨 `level-profiles.json` 出去（701 處，`[經度, 緯度, 朝洞內方位角, 系統]`）。
算繪端本來想從股道取樣反推，連試三次都是 0 個洞口——它只走「當下有車在跑」的路線，
沒車的隧道連一個取樣點都拿不到。

## 已知限制

公尺值仍是顯示估計，不是實測縱斷面或工程軌面標高，`railElevationM` 仍為 null。
`GRADE_SPAN_M=20` 是量縱坡的最小跨距——逐點取樣的斜率會被取樣噪音放大到 36%，不能直接用。
