## 1 為什麼要做

### 1.1 實測證據

用 `speak-human-tw` v1.4.0（繁中去 AI 味 skill，38 種痕跡）對軌島三段上線中的對外文字跑 annotation：

| 樣本 | 命中 |
|---|---|
| 訪客更新紀錄 4 條 | **0** |
| 首頁介紹句 | 1（半形 em dash U+2014 當中文分隔，全站 11 處） |
| 免責聲明 | 0（正確判定為保護項，不動） |
| 條 3 頓號連接分句 | 1 |

誤殺 0 起。它管得住「不像 AI」，管得不錯。

**但軌島的文字問題從來不是 AI 味。**「拉了像沒作用」「車根本不在畫面裡」「謝謝網友回報」本來就是人寫的。真正會出事的是**像不像軌島**，而那一層它結構上照不到。

### 1.2 五個空白（全部有被糾正的實例）

| # | 空白 | 實例 |
|---|---|---|
| 1 | 專屬用語表 | 08-05 更名通行證，08-09 盤點時 29 個記憶檔仍全寫 Plus，整晚對使用者講錯話 |
| 2 | 人稱裁示 | 08-21 issue #35 草稿寫「我們會認真考慮」，當場被糾正——一人專案 |
| 3 | 事實契約 | 08-10 更新紀錄寫進四個只存在於開發分支的錯誤，當天被退 |
| 4 | 通道體例 | 08-30 (1.5.1) 商店文案四連指正，535／1880／755 字元被砍到 138／388／176 |
| 5 | 控件 emoji | 08-12 更多選單的 ⭐ 被退 |

### 1.3 決定性的理由：規則跨通道互相矛盾

同一份記憶（`release-notes-filter-by-user-value.md`）同時寫著：

> 商店版本說明**禁用對比框架**：中文「不再／不會再／原本／上一版／終於／修好」、英文 `no longer / previously / used to / fixed`、日文「なくなりました／以前は／修正しました」

> App 內的更新紀錄清單「**體例本來就是前後對比體**（「原本用終點對照…於是…」），不要順手把它改成商店文案的語氣」

**同一組詞，一個通道禁用、另一個通道是正確體例。** 這不可能靠通用 skill 維持，也不可能靠記性維持——它需要一個知道「這段字要出現在哪裡」的判準。

## 2 已定案的三個決定

| | 決定 | 理由 |
|---|---|---|
| D1 | **Skill ＋ 機器 gate**，不是純 prompt skill | 使用者規則明訂「查不到守門人 ⇒ 先補 gate 再改」。純 prompt skill 就是他自己記憶檔裡的 **F1：規則存在，但沒有任何自動判準在看它** |
| D2 | **正本與 skill 都進 repo** | 單一正本，gate 直接讀，跟 commit 走。代價：GitHub 上公開（但 `.claude`／`docs`／`scripts` 都在 `.assetsignore`，**不會上 railisland.tw**） |
| D3 | **第一版＝index.html 全面 ＋ 商店文案納進 repo** | 被糾正最多次的通道（商店文案）原本是 gate 構不到的，納進 repo 才守得到 |

### 2.1 一條公開邊界

規則本身可以公開（用語表、一人專案寫「我」都是公開事實）。
**但使用者被糾正的原話不進 repo**——那類引述留在私人 memory，skill 只帶規則不帶對話。（本檔進 repo 時已依此條自我套用，移除了原稿引用的一句原話。）

## 3 架構

三個檔，各有單一職責：

```
docs/voice-rules.json                        ← 機器可讀正本（surfaces 定位 + 詞表 + 結構判準）
scripts/check_voice.mjs                      ← gate，讀正本，掛進 ship_web.mjs preflight
.claude/skills/railisland-voice/SKILL.md     ← 散文層：怎麼寫、過濾判準、通道體例
```

**單一正本原則**：詞表與 surface 定位**只寫在 `voice-rules.json`**。`SKILL.md` 引用它、不複述值。
理由：防 F6（判準跟著症狀漂移、正本沒跟上）。兩份規則就是漂移的溫床。

**掛載點**：`scripts/ship_web.mjs` 的 preflight（目前第 64 行跑 `check_i18n.mjs`、第 73 行跑 `check_deploy_config.mjs`），`check_voice.mjs` 接在它們後面。
理由：使用者記憶明訂「**不在出貨鏈上的驗收腳本等於不存在**」——`verify_plus_subscription.mjs` 就是這樣讓 App 線首層養到 12 條、長出兩份重複正本，一路出到 Android 1.5.0 都沒紅過。

## 4 Surface 模型（核心設計）

### 4.1 問題

`index.html` 有 27,811 行，程式碼、註解、對外文案混在同一檔。而規則本身明訂 `PLUS_ENABLED`／`plusOpen()`／`plusConfigured()`／`/api/plus-status`／RevenueCat 的 `entitlement: 'plus'` **一律不准改名**（RevenueCat 的 id 是外部契約，改了所有已購買者資格判定失效）。

實測：檔內「Plus」相關**程式碼識別字 70 處**，**對外文字 2 處**。裸 `grep Plus` 會誤殺 70 個必須保留的識別字。

判準必須先能回答「**我在量的是誰**」。

### 4.2 決定：白名單 surface

`voice-rules.json` 宣告每個對外文字容器：

```json
{
  "id": "changelog-canon",
  "file": "index.html",
  "locator": { "type": "regex", "pattern": "<li data-cl=\"[^\"]+\">.*?<span>([^<]+)</span>" },
  "channel": "changelog",
  "kind": "content"
}
```

`channel` 決定套哪組規則——**這就是解決「跨通道矛盾」的機制**。

### 4.3 第一版的 surfaces（定位法全部已實測驗證）

| id | 檔 | 定位 | 實測數量 | channel |
|---|---|---|---|---|
| `changelog-recent` | `index.html` | `<li data-cl-of="…">` 的第二個 `<span>` | 8 | `changelog` |
| `changelog-canon` | `index.html` | `<li data-cl="…">` 的 `<span>` | 96 | `changelog` |
| `content-blocks` | `index.html` | 沿用 `check_i18n.mjs` 的 `evaluateConstBlock`：`ACHIEVEMENTS`／`STATION_INTRO`／`HELP_QUICK`／`HELP_GROUPS`／`SYS_META`／`GROUPS`／`METRO_OFFICIAL` | 7 區塊 | `ui` |
| `i18n-dict` | `i18n/translations.js`（627 行）、`i18n/content-translations.js`（824 行）、`i18n/legal-translations.js`（207 行） | 模組匯出的字典值 | 3 檔 | `ui` |
| `whatsnew` | `app/scripts/set-release-mode.mjs` | `MODES[*].why` 字串 | 表內每個 mode | `whatsnew` |
| `store-copy` | `app/store-copy/<version>.{zh-Hant,en,ja}.txt` | 整檔 | **新建** | `store` |
| `ui-control` | `index.html` | 真 HTML `<button>`／`<summary>` 的可見文字（先剝除 `<style>`／`<script>`） | 24 處符號 | `control` |

**⚠️ 一個修正**：`RAIL_APP_WHATS_NEW` **不是** index.html 裡的三語常數（我原本這樣以為，查證後是錯的）。它由 `app/scripts/prepare-web.mjs` 在 App build 時注入，文字來源是 `set-release-mode.mjs` 的 `MODES[mode].why`，**單語繁中、沒有 `_EN`／`_JA`**。已依實況改寫上表。

### 4.4 🔴 S0：surface 覆蓋率斷言（第一條，也是最重要的一條）

**每個宣告的 surface 都必須在目標檔裡定位成功、且抓到 ≥1 條文字。任一 surface 抓到 0 條 ⇒ FAIL。**

理由有二，都有前例：

1. **防 F2（守門人自己死掉，沒有訊號）**——正本 gate 曾從 09:48 起沒載入，**8 顆 commit 在它缺席下「通過」**。
2. **覆蓋率本身要有具名斷言**——只把 N/M 印在 detail 等於沒 gate，分母會無聲縮水（前例：比對清單裡塞一個打錯字的選擇器，覆蓋率 16/16 掉到 16/17，卻沒有任何斷言擋它）。

**⚠️ S0 的守備範圍要說準**：它擋的是「**宣告了卻定位失敗**」（改動 index.html 把標記弄斷、檔案改名、區塊被刪）——那種情況會當場紅，不會靜默少驗一塊。

它**擋不了「根本沒宣告」**：日後新增一個全新的對外文字容器而沒登記進 `surfaces[]`，S0 對它一無所知。那道缺口沒有機器解，只能靠 §6 第 9 條寫進 skill 的檢查表，由人在新增時同輪註冊。**這條限制要明文寫在 gate 的輸出裡**，不要讓「S0 綠」被讀成「所有對外文字都驗過了」。

## 5 Gate 規則（機器判得動的那些）

| 編號 | 規則 | 套用 channel | 判準型態 |
|---|---|---|---|
| **V1** | 對外不得出現 `Plus`／`軌島 Plus`／`月費方案`／`年費方案` | 全部 surface | 詞表比對 ＋ allowlist |
| **V2** | 對外不得出現 `我們`／`本團隊`／`敝團隊` | 全部 surface | 詞表比對 |
| **V3** | 更新紀錄首層 ≤50 字、主題組 ≤80 字 | `changelog` | 字數 |
| **V4** | 商店文案體例：一項一行、段落之間空一行、不得有小標、不得有版號抬頭 | **僅** `store` | 結構 |
| **V5** | 商店文案不得用對比框架（中英日三組禁詞） | **僅** `store` | 詞表 |
| **V6** | UI 控件不得**新增**符號（棘輪，見 §5.4） | **僅** `ui-control` | 基線差集 |
| **V7** | 三語 store-copy 條目數一致 | `store` | 計數比對 |

### 5.1 🔴 V1 必須有 allowlist（已實測證實必要）

更新紀錄裡**有兩條合法引用「Plus」的歷史條目**：

> 8/5 「軌島 Plus」正式更名為「軌島通行證」，兩種自動續訂方案改稱月票與年票…

> 8/5 TestFlight 測試版的 App Store 測試訂閱現在會完整開啟通行證…

沒有 allowlist，V1 上線第一天就把更名公告本身判成違規。

**allowlist 機制**：`voice-rules.json` 的 `V1.allow[]` 收「這條 `data-cl` id 的這個詞是歷史引用」，每筆必填 `why`。
**且 allowlist 本身要有斷言**：每筆 allow 都必須真的還命中得到——命中不到代表那條文字已改，allow 該刪，否則 allowlist 會慢慢腐爛成一張「反正都放行」的清單。

### 5.2 🔴 V5 只掃 `store`，不掃 `changelog`

這是第 1.3 節那個矛盾的落地。更新紀錄的前後對比體是**正確體例**，掃它就是把對的東西判成錯的。

驗收要求：**必須有一條反向對照**——拿一條真實的 changelog 對比體例餵給 V5，斷言它**不**開火。否則沒人知道 channel 分流有沒有真的生效。

### 5.3 V3 的 50／80 是合法的硬常數

使用者記憶裡有一條「判準寫**是什麼／怎麼排**，不寫**有幾個／幾 px**」，硬寫數字通常是反模式。

**V3 是例外，且理由要寫進 json 的 `why` 欄位**：50／80 是使用者**明文定案的體例上限**（「首層每條 ≤50 字、主題組內 ≤80 字，長了就是走回頭路」），不是某次量測到的當下值。體例常數不會因為別人的正常操作而漂移。

順帶：**這兩個上限目前零守門人**（已查證，`check_i18n.mjs` 只守條數與正本配對，不守長度）。

### 5.4 🔴 V6 是棘輪，不是絕對判準

**原案已作廢。** 原本寫「用 Unicode Emoji property 判斷控件有沒有 emoji」，實測資料證明那是錯的判準。

#### 為什麼原案錯

**（a）第一天就會誤殺 16 種、24 處已上線且從未被點名的控件符號：**

| | 符號 | 出處 |
|---|---|---|
| ◎ ×3 | `◎附近車站` | |
| ↗ ×3 | `↗ 行程分享`、分享鈕 | |
| ❚ ×2 | `❚❚暫停` | |
| **⏺ ×2** | `⏺錄影` | **U+23FA 本來就在 Emoji 集合裡** |
| ♪ ×2 | `♪音樂` | |
| ✕ ×2 | 各關閉鈕 | |
| ⚠ ×1 | 營運通阻公告鈕 | |
| ☰ ×1 | `☰更多` | |
| **⏭ ×1** | `⏭換首` | **U+23ED 同樣在 Emoji 集合裡** |
| → ◐ ▴ ▾ ⋯ ↓ ◌ 各 ×1 | 方向／外觀／曲線／時刻表／更多／匯出／放空模式 | |

`⏺` 與 `⏭` 是決定性證據：字元表判準對它們**必然開火**，而它們是已接受的控件。

**（b）判準被偷換了。** 裁示原文寫得很清楚：

> 注意 U+2B06⬆、U+2606☆ 這類「文字符號」在 iOS 也可能渲染成 emoji——**判準是 iOS 實機／WebKit 渲染結果，不是字元表分類**

規則的判準是**渲染事實**。靜態 gate 讀字元讀不出渲染結果。用字元表分類去實作它，就是 F6（判準跟著症狀漂移、正本沒跟上）。

**（c）真正該抓的東西還沒發生。** 控件上現在**一個彩色 emoji 都沒有**——⭐ 與 ⬆ 08-12 已清掉。gate 要抓的是「下次有人又加一個」。

#### 改案：棘輪

沿用 `verify_rules_coverage.mjs` 已驗證過的機制——「**只准降不准升。一律紅會被無視，只擋惡化才有牙**」。

1. 上面那 16 種符號寫進 `voice-rules.json` 的 `V6.baseline`。
2. V6 只在 `ui-control` surface 出現**基線以外的新符號**時 FAIL。
3. 基線只准縮、不准擴——要擴必須是使用者當輪明示，且 json 裡記 `why` 與日期。
4. `icon-table`（`RAIL_EMOJI`，成就與車站設施那 24 個圖示）**完全不掃**——那是內容區，新增成就本來就會新增圖示。

| | 絕對判準（原案） | 棘輪（本案） |
|---|---|---|
| 第一天誤殺 | 16 種 / 24 處 | **0** |
| 抓得到 08-12 那顆 ⭐ 嗎 | 抓得到 | **抓得到**（新增的） |
| 要不要解「iOS 會不會上色」 | 要，而且解不了 | **不用** |
| 新增成就徽章時 | 誤殺 | 不掃內容區，不受影響 |

**已知代價（明文承認）**：基線裡的符號日後若真在 iOS 上被渲染成彩色 emoji，gate 不會提醒。那件事本來就只有實機看得出來，gate 從來答不了——寫在 skill 的檢查表裡交給人判斷。

**這也讓「控件 vs 內容」那一刀的風險降級**：切歪的代價從「16 種假紅」變成「某個新控件沒被監看」，而後者由 S0 覆蓋率斷言擋。

### 5.5 商店文案字元數只警告、不 FAIL

繁中 ~140／English ~390／日本語 ~180 是 1.5.1 **定稿時量到的值**，不是體例常數。寫成硬門檻，下次改文案必假紅，然後整支腳本的輸出開始被忽略。

⇒ 印警告、附上一版的實際值當參考，判準交給 V4 的結構條件。

## 6 Skill 規則（gate 判不動的品味層）

`SKILL.md` 負責這些，全部無法機器化：

1. **過濾判準**：逐條問「使用者看更新說明時在乎嗎」。1.5.1 實際刪掉的：動態島圓角留白、擁擠度比對邏輯細節、斷線提示歸因、彎道速限公里數。
2. **事實契約**：那個缺陷**有沒有真的到過使用者手上**。只活在開發分支／預覽站、上線前就修掉的，一個字都不寫。
3. **通道體例對照表**：更新紀錄（對比體，用戶語氣）vs 商店文案（平鋪直敘，禁對比）vs App Review Notes（四段內，只寫審核員誤判風險）vs issue 回覆（第一人稱單數）。
4. **語域**：一般用戶看得懂，不是工程術語；「（謝謝網友回報）」是既有慣例。
5. **不替回報者寫恭維**：不確定他之前想過沒有，就據實寫或省略。
6. **同一功能又修一次＝改既有那條**，不新增第二條。
7. **一律繁體中文**（含 commit message）。
8. **新控件的符號要用實機判**：V6 的棘輪只擋「基線外的新符號」，答不了「這個符號在 iOS 上會不會被渲染成彩色 emoji」——那是渲染事實。新增任何帶符號的控件，skill 要提醒去 WebKit／實機看一眼，並優先改用 inline SVG（`stroke: currentColor`）。
9. **新增對外文字容器要同輪註冊進 `voice-rules.json` 的 surfaces**，否則 gate 少驗一塊（S0 只擋「宣告了卻找不到」，擋不了「根本沒宣告」）。

### 6.1 明文標示「無守門人」的通道

skill 要明講：**GitHub issue 回覆、社群貼文、commit message、App Review Notes 這四個通道沒有 gate**，本質上不在 repo。它們只靠 skill 被讀到。

這句話本身就是價值——使用者記憶裡的 F1 之所以危險，是因為沒人知道哪些規則沒有守門人。誠實起點：他的規則正本 75 條裡只有 17 條有守門人。

## 7 驗收：怎麼證明 gate 真的有牙

**每條 V 規則都要有突變測試 ＋ 控制組**，缺一不算完成。

| 步驟 | 動作 | 判準 |
|---|---|---|
| 1 | `git worktree add --detach` 開隔離樹 | 不污染主樹 |
| 2 | 逐條故意違反（V1 塞「軌島 Plus」進 changelog、V2 塞「我們」、V3 寫 60 字首層條目、V5 塞「不再」進 store-copy…） | **紅在預期的那一條**，不是別條 |
| 3 | 還原 | **全綠** |
| 4 | 反向對照 | V5 對真實 changelog 對比體例**不**開火；V6 對基線那 16 種符號**不**開火（尤其 `⏺`／`⏭`，字元表判準會誤殺的那兩個）；S0 拿掉一個 surface 宣告 → 紅 |
| 5 | V6 棘輪專項 | 在任一 `<button>` 塞一個基線外的符號（例：⭐）→ **紅**；在 `RAIL_EMOJI` 加一個新成就圖示 → **綠**（內容區不受管） |

🔴 **突變的還原基準不可被自己的突變污染**——zsh 解析錯誤會先跑完前半段才死，快照可能存到已突變的檔；`md5 相符` 對壞基準是零資訊。還原後要**再跑一次全綠**才算。

🔴 **突變要指名考哪一條**。前例：第一發突變（把命中半徑改成 0.01px）根本沒讓測試變紅，因為測試點的就是列車中心、距離恆 0——沒有控制組就會誤以為判準有牙。

## 8 不做（YAGNI）

| issue 回覆／社群貼文／commit message 的 gate | 本質上不在 repo，做不出誠實的判準。改為在 skill 裡明文標示「無守門人」 |

### 11.1 兩則過期資訊已修正（供日後對帳）

寫這份 spec 的過程中，有兩處我依記憶寫下、查證後證實**已過期**：

1. **`RAIL_APP_WHATS_NEW` 不是 index.html 裡的三語常數。** `_EN`／`_JA` 在檔內是 0 次。它由 `app/scripts/prepare-web.mjs` 於 App build 時注入，文字來源是 `set-release-mode.mjs` 的 `MODES[mode].why`，**單語繁中**。
2. **「內容區既有的 🛠／🗺」是舊資訊。** `🛠` 現在全檔不存在；`🗺` 只以 `RAIL_EMOJI['ach-km500']` 的形式存在。更新紀錄 104 條裡 emoji 是 **0 個**。

兩則都是「記憶檔的內容會過期，而且過期時完全沒有症狀」的實例——這正是這顆 skill 要解決的問題本身。實作時凡引用記憶的事實，一律回原始碼再驗一次。
