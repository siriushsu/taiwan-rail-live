# 公車小工具與兩層共用基礎 — 設計書

日期：2026-09-11
狀態：設計已核可，待寫實作計畫
基準：`origin/main`（本設計撰寫時工作樹落後 4 顆，動工前先併上）

## 由來

使用者看到 App「查交通」（個人開發者 Youci Huang，2026-08-27 上架，僅 iOS），
提出把它的軌道與公車功能補進軌島。盤點兩邊之後收斂成四個單元，
其中「附近公車站到站提醒的小工具」是使用者真正要的東西，其餘是它的前置或順帶。

同日 issue #55 回報 Android 小工具「自動（最近的站）」失效，
該修法正好是公車小工具「自動最近站牌」要吃的同一層，因此併入本設計。

## 已定的決策

| 決策 | 結論 |
|---|---|
| 捷運路網示意圖 | **不做**。軌島本來就是地圖 |
| 公車站牌入口 | 搜尋框擴充，**先不上地圖圖層** |
| 小工具選站 | **釘選站牌為主**，自動最近站牌當通行證加值 |
| 公車提醒型態 | **週期性出門提醒**（週一到五 / 每天 / 指定星期），不做「盯這一班」 |
| 出貨順序 | A 與 D 並行 → B → C |
| 售票 | 不做。與「查交通」一致 |

## 四個單元

| 單元 | 內容 | 相依 |
|---|---|---|
| A | 高鐵對號座餘位 | 無 |
| D | 最近站解析共用層（issue #55） | 無 |
| B | 提醒排程共用層（週期性 + 解開系統限制） | 無 |
| C | 公車站牌、到站與小工具 | B、D |

A 與 D 沒有交集，可並行。C 的提醒要 B 先落地，C 的自動最近站牌要 D 先落地。

## 單元 A：高鐵座位狀態與票價

### 目標

**這不是訂票資訊，是擁擠預告。** 軌島不賣票，所以「還能不能訂到位」本身對使用者沒有動作可做。
但訂不到對號座的人會去坐自由座，因此某班顯示售完，等於預告那班自由座會擠。
這是使用者站在月台上真正會問的問題。

🔴 **高鐵沒有任何擁擠度資料。** 2026-09-11 對 TDX 官方 swagger 清點，
高鐵全部 27 支端點裡沒有 Crowding、Occupancy、CarWeight 或載客率相關的任何一支。
既有的 `api/thsr-freeseat` 來源是 `DailyFreeSeatingCar`，那是「今天哪幾節是自由座」的每日公告，
不是即時人數，兩者不可混為一談。對號座三態是唯一買得到的間接訊號。

### 資料來源（2026-09-11 實測）

```
GET /api/basic/v2/Rail/THSR/AvailableSeatStatus/Train/OD/{起站ID}/to/{迄站ID}/TrainDate/{YYYY-MM-DD}
```

🔴 **陷阱：站碼用英文名會回 HTTP 200 加空陣列，不是 404。**
`TaipeiStation` / `ZuoyingStation` 這種寫法連續四個日期都回 `AvailableSeats: []`，
看起來像「今天沒資料」。必須用數字站碼才有資料。

站碼：南港 0990、台北 1000、板橋 1010、桃園 1020、新竹 1030、苗栗 1035、
台中 1040、彰化 1043、雲林 1047、嘉義 1050、台南 1060、左營 1070。

回傳形狀：

```json
{
  "UpdateInterval": 600,
  "SrcUpdateInterval": 600,
  "TrainDate": "2026-09-11",
  "AvailableSeats": [
    { "TrainNo": "0117", "Direction": 0,
      "OriginStationID": "1000", "OriginStationCode": "TPE",
      "DestinationStationID": "1070", "DestinationStationCode": "ZUY",
      "StandardSeatStatus": "X", "BusinessSeatStatus": "X" }
  ]
}
```

實測台北→左營當日回 75 班。

### 能力邊界（寫進 UI 文案，不可超譯）

- 只有三態：`O` 有位 / `L` 剩不多 / `X` 售完。**沒有座位數字。**
- 標準座與商務座各一個狀態。
- 10 分鐘更新一次，不是即時。
- **按起訖站對查詢**，所以畫面必須先知道使用者要去哪一站。

依「官方給的值一律照抄字面」原則：三態原樣對應三段文案，不自行合併、不自行推算數量。

### 實作：改用大量版端點，不要 OD 版

🔴 **不要用上面那支 OD 端點。** 改用 `GET /v2/Rail/THSR/AvailableSeatStatusList`。
實測一次呼叫回 94 筆，每一筆是一個班次從某站出發，並帶著 `StopStations[]`，
**逐一停靠站各自一組座位狀態**：

```json
{ "TrainNo": "1202", "Direction": 1, "StationID": "1000", "DepartureTime": "08:07",
  "StopStations": [ { "StopSequence": 6, "StationID": "0990",
                      "StandardSeatStatus": "O", "BusinessSeatStatus": "O" } ],
  "SrcUpdateTime": "2026-09-11T09:26:04+08:00" }
```

因此**不需要讓使用者先選目的地**，也不需要起訖選擇器。原設計那一段作廢。
上面的 OD 端點與英文站名陷阱保留在本文件，是給日後真的需要指定日期查詢時參考。

新增 Worker 端點 `GET /api/thsr-seat`，無參數，回精簡後的查詢表。

雙層 TTL 依既有規則設定（管上游呼叫的是 mem 不是 `s-maxage`，
實際上游間隔等於最小的 edge 倍數且要大於 mem）：**edge 300 / mem 310，實際上游 600 秒**，
正好對齊 `UpdateInterval`，不浪費配額也不落後於來源。

前端：高鐵車站看板的每一列，在使用者選定目的地之後才顯示徽章。
**沒選目的地就不顯示**，不要拿任意終點站頂替。

### 驗收

- 三態各至少抓到一個真實樣本並截圖。
- **正向對照**：故意用英文站名打一次，守門人要能分辨「空陣列」與「真的沒班次」，且要紅。
  這條反向判準沒有對照就是恆真的假綠。
- 邊界：查詢日期超出高鐵開放售票範圍時的回應形狀要驗過。

### 一併做：高鐵票價

`GET /v2/Rail/THSR/ODFare/{起站ID}/to/{迄站ID}`。台北→左營實測回 `Fares[]`，
每筆是 `TicketType` × `FareClass` × `CabinClass` 的組合價。

官方代碼定義（取自 swagger 的 `description`，**照抄，不要自己命名**）：

| 欄位 | 值 |
|---|---|
| `TicketType` | 1 一般票(單程票) / 2 來回票 / 3 電子票證(悠遊卡、一卡通) / 4 回數票 / 5 定期票(30天期) / 6 定期票(60天期) / 7 早鳥票 / 8 團體票 |
| `FareClass` | 1 成人 / 2 學生 / 3 孩童 / 4 敬老 / 5 愛心 / 6 愛心孩童 / 7 愛心優待、愛心陪伴 / 8 軍警 / 9 法優 |
| `CabinClass` | 1 標準座車廂 / 2 商務座車廂 / 3 自由座車廂 |

抽樣驗證（台北→左營，一般票成人）：標準座 1490、商務座 2440、自由座 1445；法優標準座 745。

票價幾乎不變動，做成建置期產生的靜態表即可，不必逐次打 TDX。
顯示預設只出「一般票成人」的三種車廂價，其餘代碼組合收在展開層。

### 不做

座位數字（官方只給三態）、訂票、任何自由座擁擠度的推算。
🔴 不可由對號座三態推導出「自由座幾成滿」這類數字，那是自行判斷，不是官方值。

## 單元 D：最近站解析共用層（issue #55）

### 已查證的現況（對 `origin/main`）

| 斷言 | 驗證結果 |
|---|---|
| Android 從未主動要過定位 | `requestLocationUpdates\|getCurrentLocation\|FusedLocation` 於 `app/android` **0 命中** |
| 只宣告前景定位 | `AndroidManifest.xml:175-176` 只有 COARSE + FINE，無 `ACCESS_BACKGROUND_LOCATION` |
| 唯一來源是系統快取 | `MetroWidgetData.java:382` 與 `RailWidgetData.java:1066` 都用 `getLastKnownLocation` |
| Android 無服務範圍概念 | `serviceRadius\|outOfRange\|範圍外` 於 `app/android` **0 命中** |
| iOS 有 12 公里 | `MetroNearest.swift:82` `serviceRadiusMeters = 12_000.0` |
| 守門人只守 iOS | `verify_metro_nearest.mjs:70` 用正則從 Swift 原始碼抽字面值 |

🔴 **issue #55 沒提到的一項**：台鐵小工具也有同一個病（`RailWidgetData.java:1066`）。
共用層要吃的是三個小工具（捷運、台鐵、未來公車），不是兩個。

### 不申請背景定位

`ACCESS_BACKGROUND_LOCATION` 是 Google Play 高風險審查，要權限聲明表、示範影片、
App 內顯著揭露，判準是「沒有這個功能 App 就不能用」。
軌島少了自動選站照樣能手動釘站，這個論述在審查那邊站不住，
且否決會擋更新並涵蓋所有測試軌道。iOS 也不是靠背景定位解決的。

### 四項變更

1. **前景取位並落地。** App 在前景時取一次座標寫進原生偏好設定。
   照抄 `RailPlacesPlugin.sync`（`RailPlacesPlugin.java:18-32`）既有形狀：
   收 lat/lon、驗台灣範圍（21.88–25.35 / 119.9–122.05）、寫進原生。不必新寫定位程式碼。
2. **快取「上次解析出的最近站」，不是快取座標。** 座標過期難判斷，站名短時間內幾乎不變。
3. **範圍外要清快取。** 留著的話下一輪定位失敗會退回幾百公里外那一站，而畫面看起來完全正常。
4. **退快取時卡面要標示。** 沒有標示的話，退化狀態與正常狀態長得一模一樣，
   使用者只會覺得「壞了」而無從分辨。照抄 iOS 的 `stale` 旗標一路帶到卡面的做法。

### 常數不分岔

半徑放進**產生的資料檔**（兩端都已經在讀的那類 JSON），由單一來源產生，
iOS 與 Android 都從資料讀、都不寫死。
`verify_metro_nearest.mjs` 要改成驗「資料檔的值 === 兩端原始碼期望」，
否則它只守得住 iOS 那一份。

🔴 **公車半徑不沿用 12 公里。** 12 公里是對捷運三系統實算出的天然斷點；
台鐵站密度高所以「我的地點」用 5 公里（`RailWidgetData.java:51`）。
公車站牌密度比台鐵高一個量級，**要另外實算一次斷點，不要猜**。這項實算屬於單元 C。

### 驗收

- 前景取位：開 App、退桌面，小工具在下一次刷新內顯示正確車站。
- 退快取：關定位或等窗過期，卡面仍顯示上次車站**且帶標示**，不是「還不知道你在哪」。
- 範圍外：注入遠處座標，出現範圍外卡面與距離文字，且快取被清掉。
- 點擊：noLocation 與範圍外兩種狀態點下去，**不得**出現 `__auto__` 字樣。
- 突變測試：把範圍比較的 `<=` 改成 `>=` 要有判準會紅，且指名考的是哪一條。
  控制組：全部還原後必須回到全綠。

模擬器可驗前四項；「背景放一段時間後是否真的退快取」需真機放著等。

### 待回報者確認（一句話）

請回報者打開軌島、退回桌面再看那一格，是不是立刻恢復。
是則確認本根因；否則另查。此問題不阻擋設計，四項變更在任一情況下都該做。

## 單元 B：提醒排程共用層

### 現況

- 儲存：`trainmap-local-reminders-v1`，上限 20 則（`index.html:23828-23831`）。
- 已有「走路到車站要幾分鐘」偏移，夾在 0 到 60 之間（`index.html:23868`）。可直接沿用。
- 🔴 只認台鐵與高鐵：`reminderSysOf()` 對其他系統回 `null`（`index.html:23871-23873`）。
- 🔴 末班車提醒再收窄一次：只在台鐵高鐵站顯示（`index.html:29271-29272`）。
- 🔴 一次性，沒有任何重複概念（`repeat` 於全檔只命中 CSS 的 `repeating-linear-gradient`）。
- 僅原生 App：`NOTIFY_LOCAL_ENABLED` 綁 `window.RAIL_NATIVE_LOCALNOTIFY`，是裝置端本地排程，非伺服器推播。

### 兩項變更

**1. 週期性。** 提醒項目加一個重複規則欄位：不重複 / 每天 / 週一到五 / 指定星期集合。
排程器每次觸發後重算下一次時間。既有 v1 資料沒有這個欄位，一律視為不重複，**不需要遷移**。

上限計算：一則週期性提醒算一則，不是展開成七則。

**2. 解開系統限制。** 捷運、輕軌、林鐵可設提醒。
🔴 捷運沒有車次概念，所以提醒綁的是「站 + 方向 + 時間」，不是綁車次。
這是與台鐵高鐵不同的一條路徑，不要硬套車次模型。

### 驗收

- 指定星期真的在那幾天觸發：用**釘死的假時鐘**推進一週，逐日比對。
- 舊的 v1 資料讀得進來且行為不變。
- 上限 20 則的行為在混合一次性與週期性時正確。
- 捷運提醒走「站 + 方向」路徑，不會意外要求車次。
- 🔴 驗收腳本要釘死語系與時鐘。不可用中文字串找元件，那是隱形的語系相依，
  紅起來完全不像語系問題。

## 單元 C：公車站牌、到站與小工具

### 資料來源（2026-09-11 實測）

**站牌查詢**（支援地理範圍）：

```
GET /v2/Bus/Stop/City/{City}?$spatialFilter=nearby(lat,lon,半徑)
```

**到站預估**（不支援地理範圍）：

```
GET /v2/Bus/EstimatedTimeOfArrival/City/{City}?$filter=StopUID eq 'A' or StopUID eq 'B'
```

🔴 **到站端點無法用「附近」直接查。** 實際打過，TDX 自己回
`BusN1EstimateTime is not supported to search nearby method` 加 `System.NotImplementedException`。
要「附近站牌的到站」一定是兩步：先用座標查站牌拿 StopUID，再用 StopUID 批次查到站。
因為本設計以釘選站牌為主，**主路徑根本不走第一步**，只有自動最近站牌那條加值路徑要。

🔴 `EstimateTime` 的單位是**秒**，不是分鐘。

### 🔴 取得策略：兩種 provider，優先走縣市直接來源

**TDX 不是唯一來源，而且對公車不是最好的來源。**
臺北市自己在 Azure blob 上放整份免費快照，2026-09-11 實測：

| 來源 | 一次取得 | 內容 | TDX 點數 |
|---|---|---|---|
| TDX 逐站查詢 | 約 1.5 KB | 一個站牌 | 每次 0.00068 點 |
| TDX 全市一次抓 | 9.1 MB | 台北全市 28,799 筆 | 每次 0.06 點 |
| **臺北市 blob** | **161 KB 壓縮 / 1.88 MB 解開** | **台北全市 29,299 筆** | **0** |

`https://tcgbusfs.blob.core.windows.net/blobbus/GetEstimateTime.gz`
格式 `{"EssentialInfo":…,"BusInfo":[{"RouteID":10471,"StopID":187095,"EstimateTime":"-1","GoBack":"2"}]}`。
同主機另有 `GetStop.gz`（1.37 MB 站牌全表）、`GetRoute.gz`（77 KB 路線表）、
`BusSeatEvent.gz`（35 KB 擁擠度，專案已在用）。免金鑰、免認證、不計 TDX 配額。
筆數與 TDX 那份幾乎相同 ⇒ 同一批資料，傳輸量小 56 倍且免費。

因此資料層做成 **provider 介面**，每個縣市掛一種：

- **`direct-bulk`**：抓整份快照進 Worker，所有使用者共用。成本與使用者人數完全脫鉤，
  可以高頻刷新。臺北市是第一個實作，當參考實作。
- **`tdx-per-stop`**：沒有直接來源的縣市，退回 TDX 逐站查詢，**必須嚴格節流**（見下）。

🔴 新增縣市應該是**改設定不是改架構**。provider 選擇與端點位置放設定檔，
不要把臺北市的網址寫死在邏輯裡。

🔴 `EstimateTime` 的負值（`-1` 等）與 `GoBack` 的值域**要查官方欄位說明照抄**，
不可從資料自行推測。臺北市的識別碼是數字 `RouteID`／`StopID`，
與 TDX 的 `StopUID`／`RouteUID` 不同，**要另做對照表**。

新北市實測前兩筆，與臺北同構（欄位小寫）：

⇒ 一份 provider 實作吃臺北與新北兩市，差別只有網址與欄位大小寫。桃園是逐站查詢，要另一種 provider。

### 🔴 官方欄位定義（Data.Taipei API 說明文件 v6.3，2025/09，第 4 頁逐字）

`EstimateTime`：**單位是秒**。負值是哨兵值，不是時間：

| 值 | 意義 |
|---|---|
| -1 | 尚未發車 |
| -2 | 交管不停靠 |
| -3 | 末班車已過 |
| -4 | 今日未營運 |

🔴 **`GoBack` 的意義隨資料表而異，同名不同義，這是會靜默出錯的陷阱：**

| 資料表 | 值域 |
|---|---|
| `EstimateTime` | 0 去程 / 1 返程 / **2 尚未發車** / **3 末班已駛離** |
| `BusData`／`BusEvent`／`BusSeatEvent` | 0 去程 / 1 回程 / 2 未知 |
| `Stop` | 0 去程 / 1 返程 / 2 未知 |
| `BusShape` | 0 去程 / 1 返程 / **2 迴圈** |

到站那張表的 2 和 3 **不是方向**，拿去當方向用會畫錯。臺北與新北實測值域都是 0/1/2/3，與上表相符。

### 涵蓋率是真的不均

宜蘭實測：車站周邊 49 個站牌回了 110 筆路線列，其中只有 16 筆
（約 14.5%）的 `StopStatus` 是 0，也就是真的有 GPS 推算的到站時間。
其餘是尚未發車、末班已過或當日無資料。

處理方式：**照實顯示**。`StopStatus` 的各個值原樣對應文案，
沒有即時資料就講沒有即時資料，不要用班表推估頂替，也不要留白讓人以為壞了。

### 站牌索引

TDX 的公車資料逐縣市切分，而搜尋要跨縣市，所以**建置期產生一份全台站牌索引**落成靜態檔，
比照既有的 541 個鐵道站轉乘索引做法。索引欄位：站牌名、StopUID、縣市、座標、經過路線。

搜尋框擴充成同時認公車站牌名與路線號。既有搜尋只認站名、車次、列車名。

### 小工具

卡面顯示釘選站牌的下一班與再下一班。
**免費版限釘一站**，多站與自動最近站牌比照現有捷運小工具列為通行證加值。
自動最近站牌吃單元 D 的共用層，**半徑要對公車站牌密度另外實算**，不沿用 12 公里或 5 公里。

### 配額與節流（本節是硬條件，不是建議）

先看既有公車轉乘功能 2026-09-02 的實測，那是同族成本模型最可靠的參考：
正常用量只佔月配額的個位數百分比（實測值記在本機記憶 `tdx-points-quota`，不寫進公開 repo）。
快取有效時成本隨**不同站牌數**上升，
幾乎不隨使用者人數上升，所以正常情況遠比直覺便宜。

🔴 **但最壞情況會拖垮全站。** 同一份實測：無節流時，一支腳本每 20 秒掃完 239 站
＝**不到半天就把整個月的餘額燒光**，且瞬間請求速率遠超金鑰的每秒上限
⇒ **共用金鑰被 429，台鐵與捷運即時一起掛**。

原因是這類端點**成本隨請求參數線性上升**，與 `tra-live`、`metro-live`、`klrt-position`
那種固定成本輪詢（成本 = TTL × colo 數，與請求數無關）性質完全不同。

🔴 **但以上只適用 `tdx-per-stop` 那條路。** 走 `direct-bulk` 的縣市（臺北市已確認）
完全不碰 TDX 配額，刷新頻率可以自由設定，也不需要「只在提醒時段附近刷新」那條限制。
臺北市若佔使用人數大宗，整體配額壓力會小很多。

因此本單元的三條硬條件（**第 1、2 條只針對 `tdx-per-stop`**）：

1. **新端點一定要掛 limiter。** 🔴 既有的 `/api/bus-transfer` 與 `/api/bus-leg-live`
   到 2026-09-05 為止**一個 limiter 都沒掛**，全站七個 limiter 一個都沒用在它們身上。
   本單元不可以再新增第三支沒有節流的同族端點，**並且要順手把既有那兩支補上**。
2. **快取以 StopUID 叢集為鍵，不以座標為鍵。** 以座標為鍵時用量隨使用者人數上升。
3. **資料來源署名要補。** `index.html` 的「資料來源與授權」清單目前 8 條，
   **一條都沒提公車**。政府資料開放授權條款的**署名是生效要件**，
   本單元擴大公車資料使用，署名必須同輪補上。

🔴 **動工前置：當月點數餘額只有 TDX 會員中心是權威。**
沒有任何 API 查得到，回應標頭只有每秒節流資訊。
`_專案資訊.html` 自己記的數字互相矛盾（兩個差很多的值並存），不可引用。監看的退路 `scripts/bus_tdx_usage.mjs` 目前執行回 Cloudflare API 403，
要先設 `CLOUDFLARE_API_TOKEN` 才能用，所以「先上再監看」這條路現在是空的。

### App 出貨陷阱

🔴 **在 repo 根目錄新增的前端 JS 不會自動進 App bundle。**
`prepare-web.mjs` 的複製規則只有兩條：一份逐檔字面清單，加上 `assets`／`data`／`i18n` 整棵。
根目錄新增的檔案兩條都不符，結果是 `<script src>` 404、模組 undefined、
掛載函式直接返回，**卡片完全不出現、零錯誤訊息、build 照樣成功**。
本單元若新增任何根目錄 JS，必須同輪加進那份字面清單並補守門人。

### 驗收

- 六都與非六都各抽一個站牌，實際比對 App 顯示與官方公車動態網站。
- `StopStatus` 每一個值都要有一個真實樣本對應到正確文案。
- 秒與分的換算有單元測試（這是最容易錯的一處）。
- 小工具在「釘選站牌」模式下**完全不需要定位權限**，要有判準證明這一點。
- 配額：上線後對照會員中心用量統計，確認實際成長曲線符合「隨站牌數而非人數」的預期。
