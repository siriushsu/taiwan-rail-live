# 懸賞綁定車庫場景 — 提案

2026-09-18。使用者裁示:「要的是懸賞功能本身,這個可以跟我們最近做好的四個精緻車庫綁在一起。」
本文只提案,未動任何程式與設定。

## 一句話

錄一趟校正旅程,解鎖那一款車的精緻車庫場景。**你搭的車,就是你解鎖的景。**

## 為什麼這個綁定成立

### 1. 四個已完成的場景,正好對到四款加減速仍是估值的車

| 場景 | 車款 | 現行 a / b / v | 出處 |
|---|---|---|---|
| `south-coast` 南迴・多良海岸 | 藍皮解憂 | 1.3 / 2.4 / 100 | `index.html:10112` 的 `/普快車｜普通車/` |
| `alishan` 阿里山林鐵(8 款共用) | DL 系列與林鐵客車 | 0.7 / 1.1 / 45 | `index.html:10111`,註解自己寫「登山段極慢」的估值 |
| `viaduct` 高架車站・站前街 | EMU3000 | 2.52 / 3.6 / 135 | `index.html:10116` |
| `shifen` 平溪線・十分老街 | DR1000 | 實際吃到 2.5 / 3.0 / 120 | 見下方「順帶抓到的落差」 |

對照表本身在 `train-garage-scenes.js`。

### 2. 資料需求剛好是「一趟」

合成驗算(拿 EMU3000 現行的 a/b 當真值、西部幹線十個站間、速度誤差 ±0.5 m/s):**一趟**就把 a、b 估到
±1%(1 秒取樣)或 ±2%(懸賞閘門的 5 秒)。一趟車本來就含十次起停,每次爬升段有幾十秒。

這一點決定了綁定可不可行:**一趟一景,兌換比例天生成立**。如果需要五百趟,這個綁定就不可能成立。

### 3. 回饋與貢獻是同一件事

為了解鎖多良海岸而去搭南迴的藍皮,那趟車就是校正藍皮曲線的那筆資料。不是「做雜事換獎品」,
是「你想做的事剛好就是我們需要的事」。

## 先決條件(這兩件不做,綁定無從談起)

### 1. 車庫本體尚未接線

四個場景目前只活在 `prototypes/garage-*/`。`train-garage-scenes.js` 開頭自己標了
「🚧 草案(2026-09-12):站點分派還沒經使用者裁示,也還沒有任何程式讀這個檔」,
全庫搜尋 `RailGarageScenes` 確實沒有任何讀取者。

**要先有「場景接進車庫」,才有「解鎖」這個東西可以給。**

### 2. 兩個平台的隱私申報要重做

`docs/android/PLAY-DATA-SAFETY.md`:
- 第 43 行:懸賞／GPS 校正旅程目前預設關閉,「日後開啟前必須重做本表」
- 第 88 行:那個持久 device ID 是懸賞開了之後才會開始上傳,申報分類會跟著變
- 第 113 行:把「重新開放 GPS 校正旅程」逐字列為必須重做本表的變更之一

iOS 的隱私標籤同理。這是已經寫下來的承諾,不是可以順手跳過的步驟。

## 🔴 一個必須避開的設計陷阱

**如果解鎖精緻場景的唯一途徑是交出 GPS,那就變成「要拿內容就得給定位」。**

(以下是我的判讀,不是引用條文)兩個平台的審查對「功能其實不需要定位,卻把內容綁在定位權限上」
都很敏感;而且它本身就不是好設計——使用者會感覺被收買,而不是被邀請。

**建議:每個場景都保留一條不碰 GPS 的解鎖路徑,GPS 那條只是額外給東西。**

站上已經有現成的材料:`COLLECT_MAP_ENABLED` 那條註解自己寫了「它其實不碰 GPS(資料來自既有乘車記錄)」。
所以「這個人搭過這款車」用乘車記錄就判得出來,完全不需要定位。

具體形狀:

- **門票**:乘車記錄認得出你搭過這款車 → 解鎖場景
- **加值**:另外錄一趟校正旅程 → 場景多一點東西(那趟自己的速度曲線做成一張卡、護照上多一枚校正章、
  或場景的動態天色),而不是場景本身

這樣定位是選用功能,申報也好寫;而且校正旅程的動機從「不給就沒得玩」變成「我想要那張卡」。

## 順帶抓到的一個落差(2026-09-18 更正)

**平溪線的 DR1000 現在畫出來的加減速是電聯車的值**(a 2.5 / b 3.0 / v 120),因為
`resolvePerf()` 只看 `carName`,而台鐵班表把這些車一律標成「區間車」(全表 697 班都是這個字)。

**更正:先前寫的「這條得想辦法用路線判」是多餘的——站上早就做好了,只是沒接到運動模型。**

`index.html:17429` 已經有:

```js
const DIESEL_BRANCH_IDS = new Set(['pingxi', 'jiji', 'shenao', 'neiwan']);
```

而且該處註解逐字寫著「非電化支線(平溪/集集/深澳/內灣竹中以南)跑 DR1000 柴油客車、非電聯車;
台鐵班表一律標『區間車』分不出,靠支線覆寫車種說明」。判定方式在 `:17473`,拿 `tr.stops` 去比對
`data/tra_special_trains.json` 的 `branchLines[].matchStations`;命中就在 `:17495` 把車種說明
覆寫成「DR1000 型柴油客車」。

所以**認車這件事已經上線了,只是只餵給文案,沒餵給 `resolvePerf()`**。要修的是把同一個支線判定
接進運動模型,不是重新研究怎麼認。範圍比原本寫的小很多。

(唯一要處理的是生命週期:`resolvePerf` 在 `:10130` 一帶,`state.special` 是否已載入要確認。)

## 收費功能怎麼擺(2026-09-18 使用者提出)

使用者:「其實之前我是想把這版車庫做在收費功能的。」這跟「搭車解鎖場景」直接衝突,必須先解。

**現況**:車庫不在 Plus 功能清單裡(`index.html:15803` 起那一串)。清單有機械契約——
「每一項都要對映到一個真的資格判定,由 `verify_plus_features.mjs` 稽核」,所以把車庫放進去
就要同時加真的閘門並更新該腳本的 `REQUIRED` 對映。另外站上已寫明的原則是
「列車位置、誤點資訊與系統覆蓋現在免費提供,不受訂閱影響」(`:33263`),車庫屬於加值面,放得進去。

**衝突**:如果精緻場景是招牌付費內容,那「搭車就送」就是在稀釋它。

### 建議:讓兩者賣的東西不一樣,就不會互相搶

- **Plus 賣的是場景本身** — 整座車庫、19 座場景、62 款車模,買了立刻全開,不用搭、不用等
- **懸賞給的是「這座場景裡跑的是你那趟」** — 你錄的那趟校正旅程,把速度曲線餵進場景裡的小車,
  於是場景裡的車照著你那天真正的走法起步、加速、進站;旁邊一張卡寫哪一天、哪一班、哪一段

這個切法有三個好處:

1. **不稀釋銷售**:Plus 買的是內容,懸賞給的是「你自己的那一趟」,買不到
2. **獎勵形狀對**:貢獻換來的東西應該是買不到的,否則貢獻者會覺得自己只是在打工省錢
3. **定位不上關鍵路徑**:付費的人不必交 GPS 就有完整車庫,免費的人也能用乘車記錄解鎖
   (圖鑑那套 `DEX_GROUPS` 的 `rollingStock`／`branchLines` 蓋章本來就不碰定位),
   校正旅程只是再多一層。三條路,沒有一條逼人開定位。

### 另一個選項(比較保守)

Plus = 車庫全開;懸賞的獎勵完全不碰車庫,改給護照上的校正章或獨立徽章。
銷售保護得最徹底,但綁定的故事就弱了——「你搭的車就是你解鎖的景」那句話沒了。
