## 1. 資料模型（規格照抄，不自行擴張）

規格原文：「提醒項目加一個重複規則欄位：不重複 / 每天 / 週一到五 / 指定星期集合。
排程器每次觸發後重算下一次時間。既有 v1 資料沒有這個欄位，一律視為不重複，**不需要遷移**。
上限計算：一則週期性提醒算一則，不是展開成七則。」

落成一個 `repeat` 欄位，兩種 kind：

```js
null                                  // 不重複（含所有既有 v1 資料）
{ kind: 'daily' }                     // 每天
{ kind: 'weekly', days: [1,2,3,4,5] } // 指定星期集合（ISO：1=週一 … 7=週日）
```

「週一到五」不是第三種 kind，是 `weekly` 的預設集合 `[1,2,3,4,5]`——UI 上是四顆按鈕，
資料上只有兩種。`reminderRepeatOf()` 是唯一的讀取入口：去重、排序、濾掉 1–7 以外的值、
空集合退回 `null`。**沒有遷移程式碼**，舊資料讀出來 `repeat` 是 `undefined` ⇒ 回 `null`。

「自訂」是不是被選中，用一個**顯式的** `draft.repeatCustom` 旗標記，不從星期集合反推。
反推過一版：選了「自訂」再手動勾成週一到五，按鈕會自己跳回「週一到五」，
因為集合長得一樣——**能從資料反推出來的狀態，不代表使用者的意圖也能反推**。

## 2. 排程走原生 `repeats`，不在 JS 裡展開

Capacitor `@capacitor/local-notifications` 8.2.1 兩種 schedule：

```js
{ at: Date }                                            // 一次性
{ on: { weekday, hour, minute }, repeats: true }        // 每週同一天同一時刻
{ on: { hour, minute }, repeats: true }                 // 每天同一時刻
```

選原生而不是「JS 每次觸發後重算下一次、再排一則」的理由：**App 可能永遠不會被打開**。
通勤提醒的整個價值就是使用者不必開 App，靠 JS 重排等於要求他每天開一次。

🔴 `Weekday` 是 Apple 慣例 **Sunday = 1 … Saturday = 7**，而本專案一路用 ISO **1 = 週一**。
換算只有一處（`localReminderPayloads()`）：`d === 7 ? 1 : d + 1`。
G2 對這一條做具名斷言，並單獨釘死 `sundayWeekday === 1`——週日是唯一會繞回去的值，
`d + 1` 這種寫法錯了只有週日看得出來。

## 3. 兩道上限（規格只寫了一道，第二道是實作時發現的）

規格寫的是項目數：一則週期性提醒算一則，上限 20（`LOCAL_REMINDER_LIMIT`）。
實作時發現這道不夠：**iOS 待排本地通知硬上限 64 則，超過的是【靜默】丟掉**，
沒有錯誤、沒有回報。一則「每天不同星期」的提醒吃 7 格 ⇒ **9 則就會踩到**。

所以多一道原生格位預算 `LOCAL_REMINDER_SLOT_BUDGET = 60`（留 4 格給系統／未來用途）。
兩道都在 `syncLocalReminders()` 同一個迴圈裡，先到先排，超過的項目標成 `standby`。

排序也跟著改：一次性項目照 `fireAt` 排沒問題，但**週期性項目的 `fireAt` 是錨點、永遠停在過去**，
照它排會讓重複提醒永遠排在最前面。改成照 `reminderNextFireAt()`（下一次真的會響的時刻）排。

G6 兩個情境各驗一次，且第二個是**對照組**：
- 19 則一次性 ＋ 1 則七天重複 ⇒ 項目 20（剛好在上限內）、格位 26 ⇒ 全排，`standby` 0
- 9 則七天重複 ⇒ 項目 9（遠低於 20）、格位 **63 > 60** ⇒ 必須有項目被推去候補

沒有第二個情境的話，「格位預算」那條程式碼刪掉也不會有人發現。

## 4. 格位 id 切在獨立區段

一則週期性提醒要佔好幾個原生 id，而既有一次性提醒的 id 是項目 id 本身。
兩者不能撞號，否則取消一則會順手殺掉另一則。分法：

```js
LOCAL_REMINDER_MAX_ID      = 100000000     // 項目 id 的上限（原本是 2147483647）
LOCAL_REMINDER_SLOT_BASE   = 1000000000    // 週期段起點
base = LOCAL_REMINDER_SLOT_BASE + id * 8   // 每則保留 8 格（daily 用 base，weekly 用 base+ISO）
```

`8` 是因為 ISO 星期是 1–7 再加一格 daily。最大可能值 `1000000000 + 99999999 * 8` 仍在
int32 內（`1.8e9 < 2.147e9`）——iOS 的通知 id 是 32 位元整數，溢位一樣是靜默的。
G3 對「一次性 id 段與週期段零交集」「同一則的格位不重複」「最大值仍在 int32」三件事各下一條斷言。

實測（G3 detail）：`overlap: 0`、`recurDup: 0`、`maxId: 1000000487`、`int32Ok: true`。

### 🔴 M7／M9：兩層防線互相蓋住，單發突變抓不到

清孤兒槽位有**兩層**：
1. `commitLocalReminderDraft()` 取**新舊槽位聯集**來取消；
2. `syncLocalReminders()` 把 pending 裡不在 `desiredIds` 的一律取消。

- **M7**（聯集改成只取新的）→ 23 案**全過**。因為第 2 層把同一批孤兒收掉了。
- **M9**（拿掉第 2 層的 `extra` 掃除）→ 23 案**全過**。因為第 1 層把它收掉了。
- **M10**（兩層一起拿掉）→ G8 紅。

所以 G8 考的是「這個行為還在不在」，**不是任何單一層防線的守門人**。這一點兩處註解都寫了，
免得下一個人以為刪掉其中一層會有東西擋他。

留兩層的理由不是「怕 sync 會漏」，而是 sync 那段**整個包在 `try` 裡**：
真機上 `getPending()` 拒絕時掃除根本不會執行，而那時的症狀是
**使用者關掉的提醒繼續每週響**。這是刻意的兩層，不是忘了刪。

（這一段是照 judgment.md 第七節第 7 條寫的：突變存活有兩種解釋——判準沒牙，或程式碼冗餘。
本例是後者，而分辨它們的方法是**把互為備援的那組一起突變**。）

## 7.5 版面：四顆重複鈕在 360px 折成兩行（已修）

「週一到五」在 360px 只分到 **47px** 的內容框，12px 的四個字要 **48px**——差 1px。
折行**不溢出、不被切掉**，而按鈕的 `min-height: 44px` 還把兩行整個蓋住 ⇒ **畫面以外零訊號**。
修法是字級 12→11（44px）並去掉按鈕左右內距。

守門人放在 E 案：「強制單行時這行字需要多寬 vs 框內有多寬」，配一個塞爆字串的正向對照。
🔴 **量尺自己錯了兩次，兩次都寫進註解**：
1. 第一版拿 `line-height` 當分母——這些鈕算出來是 `normal`，`parseFloat` 得 `NaN`，
   四個寬度**同時**紅（而且正向對照也是 NaN，一起失效）。
2. 第二版的對照字串只有 12 個字，在 768px（框 149px）**還是塞得下** ⇒ 對照恆真。
   改成 `'週一到五'.repeat(20)`。

**en／ja 仍會折行**（`Every day`、`繰り返さない`）——那是正確的譯文，不為了排版改字；
按鈕高 44px，兩行放得下也不會被切。

## 8. 還沒做／已知落差

- **沒有在真機上驗過**。整批的原生行為都走 `__notifyMockPending` 替身，
  驗的是「我們送給 Capacitor 的 payload 對不對」，不是「iOS 收到之後會不會照響」。
  真機要驗的三件事：64 則上限的實際行為、`repeats: true` 跨週是否真的續排、
  夏令時間（台灣沒有，但使用者出國時系統時區會變）。
- **B2 未做**：捷運／輕軌／林鐵仍不能設提醒。規格寫明捷運沒有車次概念，
  提醒要綁「站＋方向＋時間」而不是綁車次——那是另一條資料路徑，不在本批。
- **「每次觸發後重算下一次時間」在本批是靠原生 `repeats` 達成的**，不是 JS 重算。
  規格原文寫的是後者；選前者的理由在 §2，但這是一個**與規格字面不同的實作決定**，記在這裡。
- 週期性提醒的 `snapshotDelaySec` 一律存 0（誤點快照對「每週一早上八點」沒有意義），
  `localReminderEffDelay()` 是唯一的判斷點。
