# 官方資訊每日巡檢機制

2026-08-01 定案並上線。

## 為什麼

使用者原話：「以後我們需要一個每天掃每個官方資訊，然後隨時跟著更改班表的機制，我不可能都會看到或是記得。」

觸發事件是三鶯線 8/1 起營運時段由 10:00–20:00 延長為 08:00–22:00——使用者自己看到新聞才想起來要改。
同一輪順手實測發現破口比想像大得多，三個來源各有各的失效方式：

| 來源 | 當時狀態 | 失效方式 |
|---|---|---|
| TDX 機讀資料 | `data/tdx/*.json` 凍在 2026-07-16 的手動快照 | **靜默漂移，當下就已經錯了**——北捷 684 筆記錄有 179 筆班次數不同（R02 平日下行 55→58 班）、332 筆時刻值不同；高雄輕軌 152 筆有 33 筆班次數不同 |
| 官網公告 | 人工重查 | 過期就生幽靈車或缺車（v0711j 已經踩過一次，每天畫出 7.5 小時不存在的列車） |
| 台鐵 14 天窗 | 每週手動 `npm run fetch-schedule` | 窗尾到期就沒班表可推 |

## 形狀

分兩層，界線畫在「要不要讀文字」。

**偵測層** `scripts/watch_official.mjs` — 純唯讀、確定性、零判斷。只回答「什麼變了、變多少」。
可以重跑、可以被驗證、不會因為模型當天的判斷不同而給出不同結果。

**處置層** — 排程任務 `railisland-official-watch`（每天 08:30，本機，比照既有的 issue 巡檢）。
讀報告後分流：機械的自己做完並上線，要判斷的停下來列證據問使用者。

為什麼要這條界線：把「新聞裡的未來規劃」當成現況正是 v0711j 幽靈列車的成因，
那種錯只有人擋得掉；而 TDX 重抓重建是確定性的，讓人每天做只會被忽略。

## 三支探針

### 1. TDX 機讀資料

8 個營運商 × 8 份資料，逐份重抓比指紋。分兩類：

- **schedule 類**（`StationTimeTable` / `Frequency` / `FirstLastTimetable`）：只餵 `build_metro_times.mjs`，
  重建不動路線幾何與站序 → 走自動路徑。
- **structure 類**（`Line` / `Station` / `StationOfLine` / `S2STravelTime` / `Shape`）：改到會牽動線檔
  與其後處理（站位修正之類），一律停下通知。

**指紋必須正規化，否則天天假警報。** 兩層雜訊當天都實際踩到：

1. **欄位層**：`UpdateTime` / `SrcUpdateTime` / `VersionID` / `SrcVersionID` 每次回傳都動 → 剔除。
2. **陣列層**：TDX 同樣的 296 筆記錄會以不同順序回傳。KRTC 逐筆比對 0/296 筆實質不同，
   整包 hash 卻不同 → 逐筆序列化後排序再 hash。

「班次數沒變但指紋不同」有兩種完全不同的成因，報表要分開講，否則只寫「0 筆變了」讓人一頭霧水：

- **TDX 改資料格式**：當天淡海／安坑／環狀線的 `Timetables` 多出 `ArrivalTime` 欄位，
  68/68、32/32、50/50 筆全變，但一班車都沒增減——重抓一次就消失，不是改點。
- **時刻值真的動了**：同日機捷 `Frequency` 的 `OperationTime.EndTime` 00:29→00:28——這才是改點。

限流：1.2 秒間隔（同 `fetch_tdx.py`）。350ms 會被 429 掉 7 個端點；連打之後 TDX 會直接斷連
（undici 吐 `fetch failed`），兩種都要退避重試——失敗若靜靜變成「今天沒驗到」，
那正是這支腳本要防的漏。

### 2. 官網公告列表

**盯列表頁，不要釘死內容頁。** 這是 8/1 事件最重要的一課：三鶯線內容頁 `node=863`
到延長生效當天都還掛著舊的 10:00–20:00，而列表頁 `node=10003` 在 07-30 就貼出公告了。

八個來源全部實測可抽（新北捷運 21 則／台北捷運 5／高雄捷運 5／桃園機捷 6／台中捷運 14／
台鐵 12／高鐵 10／林鐵 12）。北捷、高捷、桃捷、高鐵的列表由 JS 產生，純 fetch 拿不到，
標 `render:'browser'` 走 Playwright。

抽取用通則，不為每家寫 DOM 解析器（網站改版時整支就廢了，通則只會少抓幾則）：
找「像日期」的行，往前三行取第一個不是日期也不是雜訊的當標題。

**「像日期」不能只判有沒有日期。** 頁尾的計數器與產生時間也含日期，且每次載入都不同——
突變測試當場踩到兩則：高捷「…更新日期:2026-07-18瀏覽人次:76248722」、
台鐵「本頁產生時間:2026/08/01 15:15:32」。判準寫成結構性的：**把日期本身挖掉之後，
剩下的殘渣要 ≤6 字**。真的日期欄殘渣是空的或「發布日期:」這種標籤，雜訊行殘渣一定很長。

抓到 0 則當成探針故障回報，不當成「今天沒消息」——網站改版或被擋的靜默失敗最危險。

### 3. 台鐵 14 天窗

讀 `data/tra_schedule.json` 的 `dateRange` 尾端，剩不到 5 天就觸發重抓。

## 自動上線的閘門

任一不過就停下改通知，**不硬闖、不放寬門檻**：

1. `git log HEAD..origin/main` 為空——不然自動部署會靜默退掉別人的 commit。
2. 工作樹沒有別的 session 未提交的改動。
3. 重建後 `git status` 只落在 `data/tdx/*.json` 與 `data/*_times.json`。
4. `scripts/verify_metro_times.mjs` 全綠。
5. `scripts/verify_sanying_hours.mjs` 全綠（起本機伺服器前先 md5 比對確認吐的是自己這棵樹）。
6. 部署後對正式站複驗，`/`、`/index.html`、改到的 data 路徑三者都收斂。

### verify_metro_times.mjs 的判準設計

兩類刻意分開：

- **結構**（物理不變式，與基準無關）：逐站時刻嚴格遞增、每班至少兩站、
  同起站同方向無 <60 秒發車、`days` 七天皆指到存在的 set。
- **相對**（與基準版本比幅度）：班次數變動 ≤ ±15%、首末班位移 ≤ 60 分、
  幹線最大空檔增幅 ≤ 30 分、基準有的線都還在。

**判準不寫死班數**——那是會漂移的量。門檻本身才是常數。

三個做錯過然後修對的地方，都是「判準模型錯了」不是「資料有問題」：

1. **發車間隔必須按起站分組**。捷運首班車同時從多個站發車、尖峰另有中途始發加班車
   （板南線亞東醫院那種）。初版沒分組，`R/平日/desc` 報 58 處「過近發車」，
   實測 58/58 都是不同起站、同時 06:00 發的首班車群，同起站分組後歸零。
2. **方向要用「站序 index 逐步變化的正負號總和」，不能比首末站**。
   高雄輕軌 C 是環線（38 站），首末站同為 index 0，首末比對會把順逆兩個方向併成一組，
   於是「同時 06:30 發車的順時針與逆時針兩班」被誤判成過近發車（初版報 77 處）。
3. **最大空檔要用相對基準的增幅，不能用絕對門檻**。環狀線 Y 平日上行 19:23 之後
   直到 23:03 有 220 分鐘的洞，本來就存在。寫絕對值只會逼出一個遲早被下次改點推翻的
   魔術數字；要抓的是「新長出來的洞」。

**突變測試**（判準有沒有牙的唯一證明）：五個突變全部在預期判準上變紅，控制組全綠。
砍三成班次→班次數幅度紅；時刻倒退→遞增紅；整條刪線→仍存在紅；複製一班同起站同秒的車→
過近發車紅；挖掉幹線 12:00–15:00→最大空檔 9→189 分紅。

## 刻意不做

- **新聞搜尋**（使用者裁示不納入）。8/1 這次官網列表頁其實早了兩天，
  但風險留著：若營運商當天才貼公告就沒有緩衝。
- **TDX 例行同步不加更新紀錄 li**（北捷多三班這種），只有實質改點才加——
  不然更新紀錄會被例行雜訊灌爆。
- **structure 類 TDX 變動不自動重建**：線檔有人工後處理（站位修正等），整檔重建會丟掉。

## 到期與維護

- 來源表在 `watch_official.mjs` 的 `SOURCES` 常數，新增系統加一列。
- 某來源連續回報「解析到 0 則」＝該站改版，去看一眼並更新那一列的 url／render。
- 基準存 `.cache/watch/state.json`（`.gitignore` 與 `.assetsignore` 都已含 `.cache`）。
  **變動處理完才跑 `--accept`**；沒處理完就收基準，那則明天不會再提醒，等於漏掉。
