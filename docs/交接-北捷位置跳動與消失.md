# 北捷官方列車生命週期（唯一有效契約）

> 2026-08-14 定案。這份文件取代 2026-08-13 的官方名冊／到站稽核與未驗證續推草稿；
> 被取代文件已移除，不得從 git 歷史把其中的時間刪車、班表主體或重新配對規則搬回來。

## 產品規則

1. 起點倒數第一次出現時建立一台車並分配 `vehicleId`。冷啟動若剛好在營運途中，允許用
   當下官方列建立一次初始名冊；初始名冊建立後，站間未配列不得另生一台車。
2. 同一台車會同時出現在多個車站的倒數裡。相同路線、方向與官方車號的列要合成同一台車的
   逐站 `timeline`，不是各畫一台。沒有官方車號時，沿既有事件身分延續。
3. 官方車號只用於同一路線、同一方向內的顯示與合併。抵達終點後，即使原車折返且沿用相同
   車號，也必須等反方向起點倒數出現後建立新的 `vehicleId`。
4. 車一旦建立，後續資料只能更新它。整包讀取失敗、空列、畸形資料、來源版本倒退、單列配對
   失敗、目的地改標及 ETA 前後修訂，都不得刪車、換 ID、複製車或清除跟隨。
5. 每段位置只依該車官方 `timeline` 的出發／到站秒推算。ETA 往回修時，畫面不得倒退；往前修
   時平滑追上，但官方到站秒仍是不可延後的 deadline。
6. 一般路線只在車抵達倒數第二站、官方資料確定缺少最後一段時，使用該車已觀測到的官方站間
   節奏補到終點。不得預先用整份靜態班表憑空推完整趟存在性。
7. 小碧潭與新北投支線是兩站單段例外：實測官方資料只有起點倒數，沒有對端到站列，所以使用
   靜態單段行車秒數跑到另一端，抵達即收車。
8. 唯一退場條件是抵達這一趟已知終點。沒有資料齡、缺訊秒數或「太久沒看到」的退場判斷。
9. 班表只在從未取得官方車輛資料，或使用者把模擬時鐘撥離現在時，作為整體備案；班表不得
   決定官方車的存在、身分或退場。

## 實作邊界

- `scripts/trtc_board_ledger.mjs` 的 `attachOfficialTimelines()` 只把多站倒數附加到已合併的車；
  倒數列數不能改變車輛基數。
- `scripts/trtc_official_roster.mjs` 是唯一生命週期 reducer。正常營運只有起點事件可出生，
  既有車沿自己的 `timeline` 保留到 `retireEpoch`。
- `worker.js` 把同一份 canonical timeline 寫入持久名冊與回傳 payload；frame key 也包含 timeline，
  避免同 revision 的逐站時間修訂被吃掉。
- `index.html` 的純位置函式負責官方 deadline，顯示層另以 per-vehicle 單調進度消除 ETA 回修造成
  的倒退。資料失敗只標記 hold，不清空最後成功名冊。
- 舊班表校正路徑仍可替班表動畫算 shift，但它的「配不到」只代表那筆 shift 不採用，絕不可
  影響官方名冊。

## 必跑驗收

```sh
node scripts/verify_trtc_official_roster.mjs
node scripts/verify_trtc_official_worker.mjs
node scripts/verify_official_roster_frontend.mjs
```

驗收必須同時包含：

- 同車多站倒數只產生一個 ID，兩個方向各有案例。
- 空輪與長時間缺訊不刪車；目的地與 ETA 修訂不換 ID。
- 站間未配列不出生；反方向即使同車號也用新 ID。
- 一般線補唯一末段；G_XBT／R_XBT 四個方向走單段例外並在對端退場。
- ETA 回修位置不倒退，前修平滑且到站秒準時落站。
- Chromium 與 WebKit，各跑 360／375／414／768 px 真觸控；車數、命中、溢出與控件碰撞均驗。
- mutation 必須證明任何缺訊 timeout、配不到刪車、終點不停退場或跨方向共用 ID 的改動會轉紅。

## 2026-08-14 驗收結果

- 後端生命週期：28/28 契約、9/9 mutation；保存的尖峰語料 80 輪、九線雙向，ID 無重複、
  不跨方向、退場後不復活。
- Worker 持久化：空輪保留既有 ID，同 revision 修訂採 fresh frame，舊 frame 不覆寫較新時間軸。
- 前端：6/6 純函式 gate、10/10 mutation。
- 真實瀏覽器：Chromium／WebKit × 360／375／414／768 共 8 組全通過；每組 4/4 合成官方車可畫、
  rAF 到站準時、位置單調、零 pageerror、真觸控可命中、零水平溢出與零控件相交。

若未來資料源契約真的改變，先保存新原始樣本、更新這份契約與正反測試，再動產品；不得先加
推測性的刪車或重新認車規則。
