# 月台乘客零件庫 2026-09-24（2026-09-26 退件修二輪，協調端稱「Task 7 第三輪」；同日主對話收件修頭髮與帽子）

目的：供高架月台停站開門功能（車庫 viaduct scene 03）的 Task 8 用——一組可在執行期用 `InstancedMesh`
以不同零件組合、不同色調（tint）拼出多種外型乘客的 Blender 匯出資產，讓月台上「上下車的人」不必逐一
建模，而是從 16 個零件按規則挑選＋著色＋擺姿勢組成。

沿用車模（emu3000）系列的 Q 版圓潤風格：頭稍大、不做五官、不含文字／商標、不影射真實人物。延續
`scripts/blender/emu3000-20260912/blender_parts.py` 的原語（`box`／`cyl`／`rod`／`mesh`）與
`emu3000-doors-20260924/build_pantograph.py` 的自製匯出迴圈（`calc_loop_triangles` +
`corner_normals`，一律非索引匯出：24 bytes/vertex＝pos.xyz+normal.xyz）。兩輪退件修陸續在
`build_people.py` 內加了四個自製建模函式（`rod_round`／`domed_cyl` 見「退件修一輪」，
`uv_sphere`／`rod_hemi_top` 見「退件修二輪」），彌補 `blender_parts.py` 原語
`box`／`cyl`／`rod` 一律用平頂 n-gon 封蓋端面、無法做圓潤造型的限制。

與 emu3000 系列的差異：本零件庫沒有既有正式資產要合併（emu3000 需要 `install_assets.py` 把外觀從
BASE commit 還原），`build_people.py` 直接一次寫出中繼檔與正式資產，不需要另外的安裝步驟。

## 重跑方式

```sh
# 建 16 個零件、自檢 P4/P5/P6、寫出中繼 .blend 與正式資產（快，約數秒）
/Applications/Blender.app/Contents/MacOS/Blender -b --factory-startup -t 4 \
  --python scripts/blender/people-20260924/build_people.py

# 讀已安裝的正式資產（不是 build 階段的 .blend——Task 4/5 教訓：匯出後的檔案才是唯一真相），
# 依 Task 8 Step 6 的組裝矩陣重建幾何，畫兩張一覽圖（較慢，數十秒到一兩分鐘，视 GPU/CPU 而定）
/Applications/Blender.app/Contents/MacOS/Blender -b --factory-startup -t 4 \
  --python scripts/blender/people-20260924/render_people_sheets.py

# 驗收
node --no-warnings scripts/verify_garage_stop_assets.mjs P   # P1～P9，共 9 項（第三輪退件修新增 P7～P9）
node --no-warnings scripts/verify_garage_assets.mjs          # 62 款既有資產完整性（本零件庫不影響它們）
```

固定輸出（不受參數控制）：
- `output/people/NOTES.md`：施工筆記（append-only，兩支腳本都會寫），含每個零件的三角形數、
  P4/P5/P6 自檢結果、一覽圖排版說明。
- `output/people/build/people.raw.bin` + `.meta.json` + `.blend`：中繼產物，不進 repo，供除錯用
  （`.blend` 是可編修場景另存，物件本身以自己的轉軸為世界原點，方便直接核對局部座標）。
- `output/people/contact-sheet.png`：14 個人物一覽（12 種站姿造型＋1 走路中＋1 坐著），**兩排各 7
  人**（退件修後的版面，見下方「退件修一輪」第 5 點）。
- `output/people/parts-sheet.png`：16 個零件各一格、標上零件名，4×4 網格。
- `output/people/people-sheets.blend`：`render_people_sheets.py` 的場景另存。

正式輸出（會進 repo）：`rail-3d/assets/garage-people-v1/people.json` + `people.bin.gz`，schema
`garage-parts-v1`，由 `build_people.py` 直接寫出（無安裝步驟）。

## 退件修一輪（2026-09-26）：四個缺陷與修法

第一輪交付（16 個零件、`共 27 項：FAIL 0`）被退件，四個缺陷全部針對「零件的立體造型」，不動 rig／
perPerson／pivot 等結構性規格。修法與理由：

1. **正面看是禿頭**——三款髮型（short/long/bun）原本只包住頭的後半，從相機正面（+X 往 −X 看）幾乎
   看不到頭髮。根因是舊版髮罩（icosphere）圓心偏移到頭後方，且半徑不夠大。改法：`HAIR_CAP_LOC` 改成
   與頭同心 `(0,0,HEAD_CZ)`、`HAIR_CAP_R` 從 .16 調到 .195（含頭頂與頭側），long 的馬尾方塊、bun 的
   丸子頭球體位置同步外移配合新的髮罩範圍。探針的正面射線測試（頭頂 1/3、頭部 y 全範圍，從 +x 往 −x
   平行射線）三款髮型的 `hairFront.ratio` 都從不合格拉到 **1.000**（每一條射過頭部上 1/3 範圍的射線，
   第一個命中都是頭髮，不是頭皮），同時 `hat.hair.*.outsideHat` 維持 0、`overHatTop` 維持 ≤0（戴帽子
   時頭髮仍完全在帽子外框內、不會穿出帽頂）。
2. **行李箱拉桿頂碰不到手**——原始 brief 給的拉桿座標本身有誤（協調端已承認），本輪改用協調端重新
   推導的目標：拉桿頂端局部座標 ≈(.03,0,.94)，對齊 Task 8 组裝矩陣 `T(−.35,−shoulder.y,0)·Ry(.35)`
   轉換後落在右手中心 (0,−.2,.87) 附近。改法：`acc-suitcase` 的拉桿用 `p.rod()` 從 (−.06,0,.52) 到
   (.03,0,.94) r=.025。探針量到的 `suitcase.topToHand` 從 .194 降到 **.026**（門檻 ≤.05），
   `suitcase.minZ`（現為 0）仍在 [−.02,.02] 內，行李箱本體尺寸未變。
3. **上身是平肩罐頭、不符合「頭稍大」的 Q 版比例**——四款上身原本是 `blender_parts.py` 的 `cyl()`
   直接拉出來的八角柱，端面是平頂 n-gon（肩膀是平的），且肩寬大於頭寬，看起來像罐頭而不是人。改法：
   新增 `domed_cyl()`（圓柱體＋四分之一圓剖面的穹頂、頂端收攏到單一極點，取代平頂 n-gon），四款上身
   全部改用它建模（`BODY_R=.16`／`DOME_H=.13`／`Z_DOME0=1.17`）；同時把 `HEAD_R` 從 .15 加大到 .16、
   夾克翻領從 (.10,.05,.16) 縮到 (.08,.03,.16)（避免翻領的平頂面積把 torsoUpFlat 撐回超標）、連帽衫
   帽子從 (−.08,0,1.33) r=.13 移到 (−.02,0,1.33) r=.11（避免往後凸出讓 backpack 的穿入判定超標）。
   四肢與鞋子也一併圓潤化：新增 `rod_round()`（兩端從全徑環往內收攏到端點的極點，取代 `rod()` 的平頭
   端面）用在手臂與腿，鞋子改用非均勻縮放的 icosphere 橢球（新增 `icosphere()` 的 `scale` 參數）取代
   長方體。探針結果：`proportion.torsoUpFlat` 四款從 .66～.78 降到 **.181～.222**（門檻 ≤.25，夾克
   最貼近上限但仍有餘裕）；`proportion.headOverMaxShoulder` 從 .75 升到 **1.026**（門檻 ≥.9，頭寬
   已略大於最大肩寬，肉眼可辨「頭比肩膀大」）；`backpack.intoTorso` 四款維持在 [.02,.04]（門檻
   [0,.05]）；`handbag.inLeftLeg`／`inTorso` 維持 0。rig（hip／shoulder y=.2／neck／height=1.7）與
   P3 的 `|y|≤.25` 全程未動。
4. **手臂露出皮膚**（襯衫/外套下手臂卻是膚色，不合理；上身有長袖時手臂應該同色）——改法：`arm` 的
   tint 從 `skin` 改成 `top`（`hand` 維持 `skin`，只有手臂跟上身同色，手掌不受影響）。這是本輪唯一
   的著色改動，不影響幾何。

修法過程中曾在 `rod_round()` 第一版把端點的極點往端點**外側**再推出去 `cap` 的距離（而不是把整圈
往**內**收攏到端點本身），加上放大後的髮罩，讓組裝後身高摸到 1.765（P2 上限 1.75，探針本身不驗
P2、是重跑不可改的正式 `verify_garage_stop_assets.mjs` 才抓到）——已改寫 `rod_round()` 讓極點精確
落在原始端點上（環往內收攏，不外推），並把 `HAIR_CAP_R` 從 .20 收斂到 .195，重新確認 P2 通過
（`height=1.75`，剛好卡在上限，`minZ=-0.005`）。**若之後還要再加大頭髮或頭部尺寸，height 的安全
餘裕已經很薄，加大前務必重跑 `verify_garage_stop_assets.mjs P`。**

四肢末端與鞋頭的「圓潤」屬於規格明講的視覺判斷（沒有硬數字），`rod_round()`／橢球鞋頭已經是肉眼可辨
的收攏造型，不是平切面；探針的 `round.{fill,side}` 只是資訊性描述（無硬性門檻），可用來對照造型
變圓後 fill 值的變化（例如 `arm` 從方柱等級的 fill 上升到 .625、`leg` 上升到 .619，兩者的 side
分箱數維持在 8——圓角化沒有增加多邊形側面分段，是靠端點收攏而不是加邊數換來的圓潤感，三角形預算
因此沒有大幅上漲）。

## 退件修二輪（2026-09-26，協調端稱「Task 7 第三輪」）：三個新缺陷與修法

上一輪（見上節「退件修一輪」）探針數字全部達標並交付，但協調端放大看一覽圖後發現三個新缺陷——
根源是上一輪的判準是**單向**的（只檢查「有沒有」，不檢查「會不會過猶不及」），這輪 verify 腳本
新增 P7～P9 三組**雙向**判準（P7/P8 是本輪新加；P9 是上一輪就有、本輪沿用未改）補上另一半檢查，
同時協調端明講「上一輪 `torsoUpFlat≤.25`（上身頂朝上平面比）這個數字已經拿掉，不用再管」——
那正是把上身逼成蛋形、進而讓肩膀看起來尖凸的根因。

1. **正面看頭髮整片罩住臉**——上一輪的髮罩改成同心圓後解決了「禿頭」，但矯枉過正：三款髮型變成
   一整顆蓋住整個頭的殼，正面完全看不到臉（P7「face」子檢查：頭寬中間 60%、頭高 15%～55% 的臉部帶，
   要求 ≥90% 的射線先打到皮膚，三款髮型量到的 `face` 全部是 0）。改法：把髮罩拆成兩塊——
   `main_cap()`（`domed_cyl()`, `HAIRLINE_Z=.16` 起算、半徑 `MAIN_CAP_R=.19`、穹頂高 `MAIN_CAP_DOME_H=.11`，
   只包住頭頂與髮際線以上，前方髮際線以下故意留空給臉）＋`back_ext()`（`icosphere`，`BACK_EXT_LOC=(-.08,0,.05)`
   偏向頭後方、半徑 `BACK_EXT_R=.11`，補滿後腦勺讓側面／背面看不到頭皮）。三款髮型在這兩塊共用底座上
   疊差異化配件：long 加一片垂墜方塊（後方遮住肩後）、bun 加一顆丸子頭球體（頭後上方，從正面會微微
   露出頭頂一角，是包頭髮型正常的樣子，不是缺陷）。重跑後 P7 三款 `face` 全部達到完美的 **1.000**
   （門檻 ≥.9），`top`（頭頂上 1/3 先打到頭髮的比例）落在 **.824～.836**（門檻 ≥.6，餘裕充足）。
2. **頭浮在上身上方＋手臂頂端凸出肩膀像尖角**——同一個根因（上一輪為了壓低 `torsoUpFlat` 把上身
   穹頂做得又高又尖，導致上身中心頂端只碰到頭部底部以下 9cm，而肩線（手臂內緣往內 1cm 處）比手臂頂
   低了 16cm，手臂因此像凸出肩膀的尖角）。改法：重新調整 `domed_cyl()` 的參數，把穹頂基準面拉高到接近
   肩膀轉軸高度、縮短穹頂高度（`BODY_R` .16→.17、`Z_DOME0` 1.17→1.32、`DOME_H` .13→.08），讓上身
   中心頂、肩線、手臂頂三者的相對高度落在 P8 要求的範圍內；連帽衫的帽兜位置同步上移配合新的
   `Z_DOME0`（`(-.02,0,1.33)`→`(-.02,0,1.42)`）、洋裝的加寬量從 `BODY_R+.02` 收斂到 `BODY_R+.01`
   （配合下一點頭寬跟著變大，避免洋裝把最寬肩寬拉得比頭寬更寬）。手臂另外新增 `rod_hemi_top()`——
   底端（接手掌）維持原本 `rod_round()` 式的直錐（便宜、反正被手蓋住看不到），頂端（接肩）改用
   1 圈中間環走四分之一圓輪廓收攏、但極點仍精確落在原始端點上（不像真半球會凸出端點之外），配合
   `smooth=True` 讓頂端讀成圓潤的半球而不是尖角，同時完全不影響 P2 組裝身高（極點位置沒變）。手臂
   半徑同步從 .04 加大到 .045。重跑後 P8 四款上身的 `neck`（頭底−上身頂）全部 ≤.005（一般三款
   -0.025，hoodie 因帽兜設計是 -0.142，見下方「已知限制」的說明）、`slope`（上身頂−肩線）全部 ≥.02、
   `arm`（手臂頂−肩線）全部落在 [-.02,.04] 區間內、`gap`（手臂與上身之間的縫）全部 ≤.005（一般是負值，
   代表手臂內緣已經插進上身範圍、完全無縫）。
3. **（隨修法 1／2 一併處理，非獨立缺陷）頭寬比例**——重新調參的過程中，P8 新增的「頭寬 ≥.9×最寬肩寬」
   子檢查第一次重跑量到 **.801**（不合格），排查後發現根因不是設計比例本身，而是量測工具的系統性
   誤差：頭部原本用 `icosphere`（細分等級跳躍、無法微調水平分段數），改份後改用新寫的 `uv_sphere()`
   （可指定經線數 `n` 與緯線環數 `rings`），但初版 `uv_sphere()` 的水平角度取樣沒有相位偏移，`n=10`
   時没有任何頂點精確落在 ±Y 軸上（最近的頂點偏 18°），量測頭寬的外框 `|y|` 因此只量到約 95.1% 的
   真實半徑。修法兩步：(a) `uv_sphere()` 永久加上 `phase=π/n` 的角度偏移，讓偶數 `n` 一定有兩個頂點
   精確落在 ±Y 軸（不是繞過測試的一次性 hack，是量測正確性的通用修正）；(b) `HEAD_R` 從 .16 加大到
   .175（同步把洋裝的加寬量從 +.02 收斂到 +.01，避免洋裝把最寬肩寬拉得比頭更寬）。重跑後
   `head=0.972`（門檻 ≥.9）。加大 `HEAD_R` 前有先確認對 P2 身高的影響（頭頂從局部 z=.29 升到 .305，
   仍在身高上限之前有餘裕）——見下方「已知限制」。
4. **帽子改款**——協調端要求把原本的高帽款式改成日常款（棒球帽／漁夫帽），帽簷朝前，且仍要完全
   罩住三種髮型（P7 的 `outHat`／`overHat` 子檢查）。改法：`acc-hat` 從對稱的「圓錐帽冠＋全周帽緣」
   改成不對稱的棒球帽——`p.cyl()` 的低矮帽冠（半徑 .21、高 .28，n=8）＋`p.box()` 的薄平帽簷（只在
   +X／前方一側，厚度僅 .02，寬度 .28×.22，不環繞整圈）。重跑後 P7 三款髮型的 `outHat` 全部是 0、
   `overHat` 全部 ≤0（帽簷以上的頭髮完全在帽子外框內、不高過帽頂），視覺裁切檢視（見下方「本輪視覺
   複驗」）確認帽子讀起來明顯是棒球帽輪廓，不再是尖頂高帽。

**視覺複驗**（協調端本輪要求：裁切放大一覽圖的頭部與肩膀、走路造型的側面，肉眼核對）：從
`output/people/contact-sheet.png` 裁出 4 張頭肩正面特寫（short／long／bun／hat 各一，2 倍放大存在
`output/people/crops-round3/head-shoulder-{short,long,bun,hat}-2x.png`）＋1 張走路造型側面特寫
（`output/people/crops-round3/walk-side-2x.png`）。逐張目視確認：瀏海下方是清楚的膚色臉、頭與身體
相接處沒有懸空縫隙、肩膀是圓潤曲線（不是平台也不是蛋形尖角）、手臂頂端與肩線齊平且緊貼身體側面
（沒有凸出的尖角）、棒球帽帽簷清楚可辨且朝前、走路側面的後腦勺被長髮的垂墜片完整遮住、全部造型都
沒有五官與文字。hoodie＋bun 那張特寫額外用來覆核 P8 `neck=-0.142`（帽兜比其他三款上身多蓋住頭部
14.2cm）是否目視也覺得異常——帽兜球體位置偏向頭後方，從正面幾乎完全被頭本身遮住，肉眼看不出破綻，
判定為誤差在可接受範圍內、不是視覺缺陷。

修法過程中沒有再踩上一輪「端點外推導致身高超標」的坑——`rod_hemi_top()` 設計時就刻意保留「極點
精確落在原始端點」的原則（見上方第 2 點），P2 身高第一次重跑就通過，且餘裕比上一輪更健康
（`height=1.73`，上一輪是剛好卡在上限的 1.75）。

## 主對話收件修（2026-09-26）：頭頂禿、帽子像方塊

第三輪交回後，主對話自己放大看一覽圖，抓到兩個本輪自檢沒抓到的缺陷，改由主對話直接修（已經第三輪，
再退一次的成本比自己修高；帳本 Task 7 有 Ruling）：

1. **頭頂從髮罩穿出來**——`main_cap()` 的 `domed_cyl()` 穹頂只有 2 圈、極點 z=.29，比頭頂 .305 還低，

## 設計取捨

- **髮型現行是往後傾的單顆球冠**（主對話收件修，取代下一條的兩件式）：前額髮際線高、後腦蓋到後頸，
  一件就同時管住「臉露出來」與「頭頂、後腦不露頭皮」，三款髮型在同一個髮帽上疊差異化配件。
- **（已被取代）髮型改成「髮際線罩＋後腦補片」兩件式**（退件修二輪換掉一輪的單顆同心殼設計）：`main_cap()`
  （`domed_cyl()`，只包頭頂與髮際線以上）＋`back_ext()`（`icosphere`，偏頭後方補滿後腦勺），前方
  髮際線以下刻意留空讓臉露出來。三款髮型在這兩塊共用底座上疊差異化配件（long 加垂墜方塊、bun 加
  丸子頭球體），三角形數 66/78/86。舊版「單顆同心殼」設計在 P7 的臉部子檢查下無法過關（正面完全
  看不到臉），因此整個換掉，不是微調參數——這裡刻意記錄設計已被取代，避免之後誤讀成仍在用的方案。
- **上身用 `domed_cyl()` 圓柱＋穹頂變化**：jacket 在 shirt 的穹頂圓柱上加兩片翻領方塊、hoodie 加連帽
  球體、dress 直接放大圓柱半徑與拉長圓柱段——四種上身共用同一組 `domed_cyl()` 基底參數
  （`BODY_R`／`DOME_H`／`Z_DOME0`），只加/改局部特徵，避免每種上身都重新設計輪廓。退件修一輪把原本
  `cyl()` 的平頂 n-gon 換成穹頂收攏到單一極點；退件修二輪保留這個手法、重新調整三個參數
  （`BODY_R` .16→.17、`Z_DOME0` 1.17→1.32、`DOME_H` .13→.08）讓穹頂基準面貼近肩膀轉軸高度，
  解決「頭浮空＋手臂凸出」（見上節）。
- **四肢圓潤化：手臂與腿分別用不同函式**——手臂本輪改用新寫的 `rod_hemi_top()`（底端／接手掌端
  維持 `rod_round()` 式直錐，頂端／接肩端用中間環走四分之一圓輪廓收攏但極點精確落在原端點上，
  讓肩線處讀成半球而非尖角）；腿仍用一輪的 `rod_round()`（兩端從全徑環往內收攏到端點極點，取代
  `blender_parts.py` 的 `rod()` 平頭端面）——腿沒有被這輪判準點名，維持原狀。鞋子仍用非均勻縮放
  `icosphere()` 橢球。以上都刻意不修改 `blender_parts.py` 本身（那是 emu3000 系列共用的原語，
  改動範圍會外溢到其他零件庫）。
- **頭部改用 `uv_sphere()`（退件修二輪換掉一輪的 icosphere）**：一輪的 icosphere 卡在 subdivisions
  離散跳級（0/1 都是 clamp 成同一個 20 面基礎二十面體，2 才是 80 面），沒辦法直接控制水平分段數；
  二輪改成自製 `uv_sphere(n=10, rings=2)`，正面輪廓至少 10 邊、100 個三角形，且帶 `phase=π/n` 角度
  偏移確保頭寬量測不失真（見上節第 3 點）。`HEAD_R` 從一輪的 .16 再加大到 .175，強化頭比肩膀大的
  比例（見上節 `head=0.972`）。
- **鞋子用 `tint:'fixed'`**：規格只規定「tint 有六種、只有 fixed 需要 color」，沒有規定哪個零件該用
  fixed；本零件庫選鞋子固定深灰（線性 RGB [.0273,.0232,.0212] ≈ sRGB `#2E2A28`）——Q 版人物的鞋子
  多半跟外套顏色無關，且統一深色鞋在配色隨機組合時比「鞋子跟上身同色」更不容易出現視覺衝突。
  這是本零件庫的設計判斷，不是規格明文要求，交棒時請留意（若 Task 8 想讓鞋子也能配色，需要把這個
  零件的 tint 從 fixed 改回 bottom 或 accent 並移除 color 欄位，是一行 JSON 改動＋重新確認 P1）。
- **手臂跟上身同色（tint:'top'），手掌維持膚色（tint:'skin'）**：退件修的設計決定——一個零件只能有
  一個 tint，若手臂維持膚色，任何一款上身（襯衫/外套/連帽衫/洋裝）看起來都會像短袖甚至無袖，跟「長袖
  居多」的日常穿著常態不符；改成跟上身同色後，視覺上讀成「長袖」，手掌獨立於手臂保留膚色不受影響。
  代價：零件庫不支援「短袖露出手臂」這種穿搭（若未來要支援，需要新增一個獨立的 tint:'skin' 手臂
  變體零件，不能靠改這一個零件的 tint 兼顧兩種穿法）。
- **無 UV／材質**：比照 pantograph 等既有零件資產，只匯出 pos+normal，著色完全交給執行期依 tint
  類別套色（Task 8 的職責），零件庫本身不含任何貼圖或固定材質（除了上述鞋子的 fixed 色）。
- **bevel 一律 0**：`blender_parts.py` 的 `finish()` 若套用預設倒角會疊加 BEVEL modifier 產生的額外
  幾何，示意等級零件禁用；改用 `smooth=True`（平滑著色法向量）在不增加三角形的前提下維持圓潤觀感。
  退件修新增的 `rod_round()`／`domed_cyl()`／`uv_sphere()`／`rod_hemi_top()`（後兩者是二輪新增）
  一樣經由 `p.mesh(..., smooth=True)` 出圖，法向量由 `bmesh.ops.recalc_face_normals()` 自動算，
  不需要手動指定朝外方向。

## 一覽圖排版

`render_people_sheets.py` 內建 12 組手選（非隨機生成）的造型 `LOOKS[]`，加 1 組走路 `WALK_LOOK`、
1 組坐姿 `SIT_LOOK`，確保覆蓋：4 種上身、3 種髮型、4 種非空配件（背包／行李箱／手提包／帽子）各至少
出現一次，並含 2 個縮小到 .7 倍的小孩造型——手選是為了保證覆蓋度可預期，不依賴隨機種子運氣。

contact-sheet **退件修改成兩排各 7 人**（原本單排橫向，退件要求「每人至少 300px 高」，單排在原本的
相機距離下無法同時滿足寬度不爆版與逐人高度雙重限制，兩排把可用的垂直空間分給每人）：上排 7 個站姿
造型、下排 5 個站姿造型＋走路＋坐姿，兩個小孩造型排在下排最前兩格。相機取景（`VERT_SPAN`／
`HORIZ_SPAN`／`PX`）依兩排的實際 z 範圍重新計算，輸出 2756×1170px。像素量測（背景色容差比對，逐欄
掃描非背景像素的 y 範圍）確認：
- 上排 7 欄全部落在 450～471px（含頭髮與帽子在內的站姿造型）。
- 下排一般站姿／小孩造型全部落在 317～463px，兩個小孩造型（.7 倍縮放）317px／323px，仍在 ≥300px
  門檻之上、餘裕不大但確實通過。
- 下排的坐姿造型量到 **252px**，低於 300px——這是姿勢造成的，不是縮放或算繪尺寸問題：坐姿的髖部
  在組裝矩陣裡本來就比站姿低，加上腿整條轉成水平（見下方「已知限制」），整體外框天生比站姿矮；
  肉眼檢視（含裁切放大檢查）確認坐姿造型輪廓清楚可辨（頭、身體、水平腿、鞋子都看得到），不是被
  裁切或算繪錯誤。300px 門檻的原意是避免造型太小看不清楚（尤其是小孩），坐姿本身的視覺清晰度不受
  影響，這裡誠實列出量到的數字而不是隱藏。
- 走路造型（下排）量到 443px，跟一般站姿相近，姿勢差異對外框高度影響不大。

算繪用 Workbench `FLAT` 光照＋`show_cavity`（`STUDIO` 兩色 matcap 會讓陰影面色相偏移，例如深色長褲
在陰影裡看起來偏紫，`FLAT` 才是所見即所得的材質色）。

坐姿的 heading 特別設為 0（跟走路同一個側面朝向），不是規格預設的 -π/2（正面朝相機）——坐姿的腿靠
`Ry(-π/2)` 轉成水平指向局部 +X，若 heading=-π/2（正面朝鏡頭）局部 +X 會轉到世界 -Y（正對相機），
水平的腿部圓柱只會露出圓形截面、幾乎看不見；改成側面朝向後腿部清楚可辨（深色圓柱＋鞋子在末端）。
這只影響 contact-sheet 的相機取景角度，不影響 Task 8 實際組裝時的矩陣（坐姿的 heading 由呼叫端決定，
`render_people_sheets.py` 選 0 純粹是為了讓一覽圖看得清楚）。

## 已知限制

- 四肢是無關節的單一圓柱（8 邊，退件修後兩端改收攏成圓潤端點），沒有手肘/膝蓋彎折的幾何；姿勢變化
  完全靠 Task 8 規格給定的剛體旋轉（走路擺盪、坐姿 `Ry(-π/2)`），零件本身不支援分段彎曲。
- 坐姿是整條腿繞髖關節轉 90 度成水平直線，不是彎膝的 L 形——這是計畫 Task 8 給定的組裝公式本身如此
  （`leg/shoe=Ry(-π/2)`），不是本零件庫的簡化，交棒時若要更真實的坐姿（彎膝）需要改 Task 8 的公式，
  不是換零件能解決的。坐姿也是 contact-sheet 唯一一個外框高度低於 300px 的造型（見上節說明，屬姿勢
  的自然結果，非缺陷）。
- worst-case 574/600（約 96%，主對話收件修的低圓頂帽子比直筒帽冠多 30 面），餘裕只剩 26 個三角形；
  若未來要加新髮型/上身/配件，加之前務必重跑 `verify_garage_stop_assets.mjs P4` 確認仍過，且要有
  心理準備可能需要先幫既有零件省一點三角形才有空間（帽冠或髮帽降到 2 圈最省，但 2 圈正是頭頂穿出來
  的原因，降之前先重算面離球心的距離）。
- 組裝後身高（P2）現為 **1.735**（主對話收件修把 `HEAD_CZ` 降 .015 抵掉變大的髮帽；退件修二輪是 1.73）——本輪 `HEAD_R`
  加大到 .175 時有事先核算過對身高的影響，`rod_hemi_top()` 的極點也刻意鎖在原端點上不外推，兩者
  加總後第一次重跑就通過，沒有重演一輪「端點外推導致身高超標」的坑（見上節「退件修二輪」說明）。
  未來若要再加大頭部或髮型尺寸，加大前仍應重跑 `verify_garage_stop_assets.mjs P2` 確認。
- `torso-hoodie` 的 P8「頭底−上身頂」子檢查（`neck`）目前是 **-0.157**（其餘三款上身是 -0.04 上下；主對話收件修把頭降了 .015），
  代表連帽衫的帽兜球體比頭部底部高出許多、大幅重疊進頭部範圍——這個子檢查只單向禁止「上身頂低於
  頭底」（float），沒有上限，所以數值上合格；本輪視覺複驗已裁切放大這款造型肉眼核對過，帽兜球體
  位置偏頭後方、從正面幾乎被頭本身完全遮住，看起來正常、不是破綻，但這是本輪唯一一個「數值合格
  但重疊量偏大」的邊界情況，之後若連帽衫的帽兜再改設計，優先核對這個數字有沒有進一步惡化。
- `render_people_sheets.py` 的 contact-sheet 版面（兩排各 7 人、`ROW_TOP_Z`／`COL` 間距、相機取景）
  是針對目前 14 組造型手調的；若之後要在 `LOOKS[]` 加更多造型，需要同步調整相機 `frame_camera` 的
  寬高與版面分配，否則新增的人物可能被裁到畫面外，或每人可用的垂直空間被壓縮到 300px 門檻以下。
- 未做任何真人可辨識度審查以外的合規檢查（例如未特別檢查是否近似特定卡通/遊戲角色的著名剪影）；
  僅靠「無五官、無文字/商標、Q 版誇張頭身比」的一般原則自我把關。
